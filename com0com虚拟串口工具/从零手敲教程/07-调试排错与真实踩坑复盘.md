# 07 · 调试排错与真实踩坑复盘

> 这一章不改代码，专门讲"敲错了怎么定位"。
> 后半段的 6 个坑都是**本项目真实踩过并修复过**的，对照着看，理解会比只看正确代码深得多。

## 1. Visual Studio 调试基础（跟敲必备）

| 操作 | 快捷键 / 位置 | 用途 |
|---|---|---|
| 生成解决方案 | `Ctrl+Shift+B` | 只看编译错误，不启动程序 |
| 启动调试 | `F5` | 断点会命中 |
| 开始执行(不调试) | `Ctrl+F5` | 快，适合反复看界面 |
| 设/取消断点 | `F9`（点行号左侧） | 在 `StartHub()`、`Deliver()`、`OnReceived()` 各放一个 |
| 逐过程 / 逐语句 | `F10` / `F11` | `F11` 会进入方法内部 |
| 监视窗口 | 调试 → 窗口 → 监视 | 输入 `_sessions.Count`、`data.Length`、`_port` |
| 即时窗口 | 调试 → 窗口 → 即时 | 运行时执行 `_hub?.EndpointState("VCOM1")` |
| 输出窗口 | 视图 → 输出 | 看 `EmitLog` 之外，还能看绑定错误、首次异常 |
| 异常设置 | 调试 → 窗口 → 异常设置 | 勾 `Common Language Runtime Exceptions`，**抛出时**就断，方便找隐藏异常 |
| 错误列表 | 视图 → 错误列表 | 双击直接跳到出错行 |

### 三个最有效的断点位置

1. `MainForm.StartHub()` 第一行 —— 确认按钮事件真的进来了、端口解析对不对；
2. `PairHub.HandleClientAsync()` 里 `var hello = await ReadLineAsync(stream);` 之后 —— 看握手内容；
3. `PairHub.Deliver()` 第一行 —— 看 `from` / `to` / `data.Length`，一眼判断"谁没发 / 谁没接"。

### 后台线程里怎么调试

`HandleClientAsync`、`ReadLoop` 都在线程池线程上。断点照样会命中，
但**不要在后台线程里看控件属性**（可能跨线程访问），看 `data`、`_sessions` 这类纯数据即可。
需要看界面状态，切回 UI 线程的 `Ui(() => ...)` 里再断点。

## 3. 六个真实踩过的坑（含修复过程）

### 坑 1：嵌套 TableLayoutPanel 列宽塌缩 → 整个界面错乱

**现象**（用户截图反馈）：两个终端面板只剩几行标题文字散落在左上角，接收区/发送框全不见了，
右侧监控区只占一小块，顶部按钮文字被截断。

**根因**：单列 `TableLayoutPanel` 没有显式添加 `ColumnStyles(Percent 100)`，
列默认是 `AutoSize`，列宽按"内容首选宽度"算；子控件即使 `Dock=Fill` 也只有那么宽。
嵌套三层只要漏一层，整棵树就塌。

**修复**：全部改用 **Dock + SplitContainer**，没有"行列样式"这个隐藏状态。
并把「Fill 控件第一个 Add，边缘控件后 Add」写成注释固定下来。

**教训**：布局容器越"智能"，隐藏状态越多；教学/排障优先选行为可预测的。

---

### 坑 2：`SplitContainer.PanelMinSize` 在构造函数里设置 → 启动崩溃

**异常**：

```
System.InvalidOperationException: SplitterDistance 必须在 Panel1MinSize 和 Width - Panel2MinSize 之间。
   at SplitContainer.set_SplitterDistance(Int32)
   at SplitContainer.ApplyPanel2MinSize(Int32)
```

**根因**：设置 `Panel2MinSize` 时控件还没布局，`Width` 还是默认 ~150，
SplitContainer 立即校验当前 `SplitterDistance`，发现越界就抛。

**修复**：不在构造时设 MinSize（用默认 25），改为在 `Shown` 事件里设 `SplitterDistance`，并 `Math.Clamp` 留余量。

> 这个 bug 是"能编译但一运行就崩"，**必须真的启动窗口才能发现**。
> 本项目是靠一个临时 harness 启动窗体、dump 控件 Bounds 时抓到的（见 §5）。

---

### 坑 3：`SplitterPanel` 不会自动 Dock → 接收区高度 0

**现象**：`TerminalPanel` 的 `Bounds` 显示 `(0,0,200,100)`，内部 `RichTextBox` 高度 0。

**根因**：`SplitContainer.Panel1.Controls.Add(x)` 不会自动把 `x.Dock` 设成 `Fill`，
`GroupBox` 保持默认 200×100。而 `TableLayoutPanel` 的单元格会自动撑满，从那里换过来最容易漏。

**修复**：

```csharp
t1.Dock = DockStyle.Fill;
t2.Dock = DockStyle.Fill;
```

**教训**：换容器类型时，先查"它会不会自动设置子控件 Dock"。

---

### 坑 4：ASCII 编码握手 → 中文错误提示变 `?????`

**现象**：自检里"端口被占用"的中文原因打印成 `VCOM1 ??????????????`；界面里"内置终端"标签也变问号。

**根因**：`Encoding.ASCII.GetBytes("已被占用")` 会把每个非 ASCII 字符替换成 `?`；
读行时如果逐字节 `(char)b` 再拼字符串，多字节 UTF-8 同样会乱码。

**修复**：
- 写：`Encoding.UTF8.GetBytes(text + "\n")`；
- 读：按**字节**收集到 `List<byte>`，最后一次性 `Encoding.UTF8.GetString(bytes.ToArray())`；
- 客户端、服务端、`VirtualSerialPort` 三处全部统一。

**教训**：协议里只要可能出现非 ASCII 字符，就**从一开始定死 UTF-8**，别等出问题再补。

---

### 坑 5：`NetworkStream.ReadAsync` 不认 `ReadTimeout`

**现象**：如果服务端握手写成 `stream.ReadTimeout = 5000; await stream.ReadAsync(...)`，
客户端连上但不发 HELLO 时，那个 Task 会永久挂着（异步读忽略同步超时）。

**根因**：`ReadTimeout` 只作用于 `NetworkStream` 的**同步** `Read`；`ReadAsync` 要用 `CancellationToken` 控制超时。

**修复**：服务端

```csharp
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
await stream.ReadAsync(one.AsMemory(0, 1), cts.Token);
```

客户端握手用的是**同步** `Read`，所以 `ReadTimeout = 3000` 是有效的 —— 两边写法不同是有原因的。

**教训**：同步 API 和异步 API 的超时机制不一样，别混用经验。

---

### 坑 6：按钮文字裁切 + 窄窗口溢出

**现象**：`① 启动服务` 显示成 `① 启动服`，`清空监控` 显示成 `清空监`；
窗口缩到 920×560 时选项条出现横向滚动条，"清空"只剩一个"清"。

**根因**：按钮宽度按英文估算，中文 9pt 字体实际更宽；多个控件的 `Margin` 累加后超过容器宽度。

**修复**：
- 按钮加宽到 120 / 100；
- 长标签改短（`HEX 发送` → `HEX 发`、`回环模式（自发自收）` → `回环模式`），完整说明放 `ToolTip`；
- 状态标签固定宽度 130，避免启动后文字变长把整排挤开；
- 逐个减小 `Margin`；
- 监控 `RichTextBox` 改 `WordWrap = true`，长日志不被右侧裁切。

**教训**：布局要**在最小窗口尺寸下验收**，不能只在设计尺寸下看。

## 5. 布局自检：把控件坐标打出来

界面"看起来不对"时，肉眼很难判断是谁的尺寸错了。本项目用过一个很有效的办法：
写一个临时控制台 harness，链接工具源码，启动真实窗口后**递归导出每个控件的 Bounds**：

```csharp
[STAThread]
static void Main()
{
    ApplicationConfiguration.Initialize();
    var form = new MainForm();
    form.Show();
    for (int i = 0; i < 8; i++) { Application.DoEvents(); Thread.Sleep(80); }

    var sb = new StringBuilder();
    Dump(form, "", sb);
    File.WriteAllText(@"C:\Temp\layout.txt", sb.ToString());
    form.Close();
}

static void Dump(Control c, string indent, StringBuilder sb)
{
    sb.AppendLine($"{indent}{c.GetType().Name,-20} Bounds=({c.Left},{c.Top},{c.Width},{c.Height}) Dock={c.Dock}");
    foreach (Control child in c.Controls) Dump(child, indent + "  ", sb);
}
```

正常结果（默认窗口 1098×664）应该是：

```
MainForm             Bounds=(...,1120,720) Dock=None
  SplitContainer     Bounds=(0,48,1098,590) Dock=Fill
    SplitterPanel     Bounds=(0,0,636,590)
      SplitContainer  Bounds=(0,0,636,590) Dock=Fill
        TerminalPanel  Bounds=(0,0,636,295) Dock=Fill   ← 不能是 200x100
          RichTextBox  Bounds=(6,63,624,156) Dock=Fill  ← 高度不能是 0
    SplitterPanel     Bounds=(642,0,456,590)
      GroupBox        Bounds=(0,0,456,394) Dock=Fill
      GroupBox        Bounds=(0,394,456,196) Dock=Bottom
  Label               Bounds=(0,638,1098,26) Dock=Bottom
  FlowLayoutPanel    Bounds=(0,0,1098,48) Dock=Top
```

再把窗口缩到 `MinimumSize` 跑一遍，检查每个 `FlowLayoutPanel` 的最后一个控件 `Right <= 容器 Width`。
**坑 2、坑 3、坑 6 都是靠这个自检抓到的。**

## 6. 排查顺序（照着走，别乱猜）

```
编译不过
 └─ 看「错误列表」第一条 → 缺 using / csproj 配置 / 拼写

能编译但启动就崩
 └─ F5 + 异常设置勾"抛出时中断" → 看调用堆栈第一行
    （本项目是 SplitContainer 的 SplitterDistance）

能启动但界面错乱
 └─ 用 §5 的 Bounds 自检 → 找 Width/Height 为 0 或 200x100 的控件
    → 检查 Dock / 添加顺序 / 容器类型

能启动、界面正常，但点按钮没反应
 └─ 在事件处理第一行打断点 → 事件有没有绑上？
    → 看 try/catch 是不是把异常吞了

服务起来了但收不到数据
 └─ 在 Deliver() 打断点看 from/to/data.Length
    ├─ 没进来 → 客户端没发 / 握手没成功
    ├─ 进来了、to 不对 → 回环模式开着？
    └─ 进来了、找不到 target → 对端没连，看"缓存 1 帧"日志

数据显示了但乱码
 └─ 编码：UTF-8？握手是不是 ASCII？读行是不是逐字节转 char？

关窗口后进程还在
 └─ 检查 Cancel() / Dispose() / FormClosing → Shutdown()
```

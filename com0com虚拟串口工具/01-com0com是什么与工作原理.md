# 01 · com0com 是什么与工作原理

> 这一篇不装任何东西，先把概念讲清楚。理解"虚拟串口对"到底是什么，后面排错会快十倍。

---

## 1. 从一根真实的串口线说起

两台设备用 RS-232 串口直连时，不能拿一根"直通线"——两边的 TX（发送脚）会撞在一起。必须用 **Null-modem（空调制解调器）线**，把信号交叉：

```
   设备 A                          设备 B
  ┌────────┐                    ┌────────┐
  │ TX  ───┼────────────────────┼───► RX │
  │ RX ◄───┼────────────────────┼─── TX  │
  │ RTS ───┼────────────────────┼───► CTS│
  │ CTS◄───┼────────────────────┼─── RTS │
  │ DTR ───┼────────────────────┼───► DSR│
  │ GND ───┼────────────────────┼─── GND │
  └────────┘                    └────────┘
```

软件视角非常简单：**A 写进自己串口的字节，从 B 的串口读出来；反之亦然。**
串口参数（波特率、数据位、校验、停止位）只在真实电气线上有意义，它决定"一个 bit 多长"。

**虚拟串口对**就是用软件在同一台 Windows 电脑上模拟这根交叉线：创建两个端口，A 端和 B 端，把 A 的输出接到 B 的输入。于是：

- 程序甲打开 `COM5`（以为自己连着仪表）；
- 程序乙打开 `COM6`（扮演那台仪表）；
- 甲发一帧，乙收到；乙回一帧，甲收到。

这样就能在没有 PLC、没有 USB 转 485、没有串口的笔记本上，完整调试上位机的收发逻辑。

## 2. com0com 到底是什么

**com0com = Null-modem emulator**，一个开源的 **Windows 内核模式（kernel-mode）虚拟串口驱动**，GPLv2 许可，作者 Vyacheslav Frolov，官方主页 `https://com0com.sourceforge.net/`，源码与安装包在 SourceForge。

它做的事：

1. 向 Windows 即插即用子系统注册一个"总线设备"：`com0com - bus for serial port pair emulator`；
2. 每创建一对端口，再挂两个"串口设备"：`com0com - serial port emulator`；
3. 让这两个设备表现为标准串口，支持 `CreateFile`、`SetCommState`、`ReadFile`、`WriteFile`、IOCTL 等 Win32 串口 API；
4. 在驱动内部把 A 端的输出队列接到 B 端的输入队列，同时把 RTS↔CTS、DTR↔DSR 等握手信号也交叉连通。

```
┌──────────────── 用户态 ────────────────┐
│  程序甲 (COM5)          程序乙 (COM6)   │
│  CreateFile / ReadFile / WriteFile      │
└──────────┬──────────────────────┬──────┘
           │  Win32 串口 API      │
┌──────────▼──────────────────────▼──────┐
│        Windows 串口设备栈 (内核态)       │
│  ┌──────────────────────────────────┐  │
│  │ com0com.sys  总线 + 两个端口设备  │  │
│  │   CNCA0 出 ──────────► CNCB0 入  │  │
│  │   CNCA0 入 ◄────────── CNCB0 出  │  │
│  └──────────────────────────────────┘  │
└────────────────────────────────────────┘
```

**默认名字是 `CNCA0` / `CNCB0`**（第 n 对是 CNCAn / CNCBn），可以改成 `COM5` / `COM6` 这类标准名字。

配套工具（装完在 `C:\Program Files\com0com` 或 `C:\Program Files (x86)\com0com`）：

| 工具 | 作用 |
|---|---|
| `setup.exe` | 安装向导，装驱动并可选创建第一对端口 |
| `setupc.exe` | **命令行**配置工具（建/删/改名/改参数） |
| `setupg.exe` | `setupc.exe` 的图形壳，需要 .NET Framework 2.0 |
| `hub4com.exe` |  companion 工具，把一个串口的数据分发给多个程序 / 走 RFC 2217 网络串口 |

## 3. 它能做什么 / 不能做什么

| 能 | 不能 |
|---|---|
| 在一台机器上创建任意多对互联的 COM 口 | 不能把串口"变"成 USB 设备给别的电脑用 |
| 让任何只认 `COMx` 的第三方软件正常工作 | 不能跨机器通讯（跨机要配合 `hub4com` / `com2tcp` / RFC 2217） |
| 模拟 RTS/CTS/DTR/DSR 握手信号交叉 | 不产生真实电气电平，接不上真实仪表 |
| 可选仿真波特率、缓冲区溢出、数据噪声 | 不替代真实硬件的时序测试（尤其 Modbus RTU 3.5 字符间隔） |
| 与 Modbus Poll / 组态软件 / 老 DOS 软件联调 | 不是"串口抓包监视器"，抓包要另用工具 |

## 4. 三个最容易混淆的概念

**① `CNCA0` 和 `COM5` 有什么区别？**
`CNCA0` 是 com0com 设备自己的名字；很多程序只枚举"端口类（Ports class）"设备，看不到它。
把端口放进 Ports 类、起一个 `COM<n>` 名字后，这些程序才能识别。这就是 `PortName=COM#` 与 `RealPortName` 的由来（见 [03 号教程](03-创建串口对与命令行详解.md)）。

**② 波特率怎么"不生效"？**
默认 com0com 只是把字节从一端搬到另一端，按内存速度走，不按 9600bps 限速——因为两端都是软件，没有真正的 UART。
想让 `EmuBR=yes` 才按配置的波特率限速（用于测试超时逻辑）。这是**设计**，不是 bug。

**③ 为什么"一端没打开时，另一端发送会卡住"？**
默认关闭了接收缓冲区溢出仿真（`EmuOverrun=no`），驱动会一直攒着数据等对端来取，表现就像程序卡死。
给接收端开 `EmuOverrun=yes`、给发送端开 `EmuBR=yes` 即可（见 [05 号教程](05-故障排查与卸载.md)）。

## 6. 和本仓库 VComPair 的本质差别

| | com0com | VComPair（本仓库） |
|---|---|---|
| 实现层次 | **内核态驱动** `com0com.sys` | **用户态** .NET 程序 |
| 端口怎么来的 | 向 PnP 注册设备对象，`\\\\.\\COM5` 可打开 | 没有设备对象，只是 `127.0.0.1:9527` 上两个逻辑端点 `VCOM1/VCOM2` |
| 客户端怎么连 | 标准 Win32 / `System.IO.Ports.SerialPort` | 实现同一个 `ISerialPort` 接口，底层是 TCP socket |
| 谁能用 | 任何程序 | 只有"愿意连这个服务"的程序（本仓库串口助手已适配） |
| 安装代价 | 管理员 + 驱动签名 + 可能要开测试模式 | 双击 bat 即可 |
| 危险程度 | 内核驱动，装错影响系统稳定性 | 只监听本机回环，关掉窗口就没了 |

可以把它理解成：

- com0com = **在操作系统里"造"了两个真的串口**；
- VComPair = **在应用层"演"了一根串口线**，对已经适配的程序来说效果一样。

> 关键知识点：`ISerialPort` 抽象让这两种实现可以无缝互换。这正是工业软件里"传输层抽象"的价值——见
> `项目/src/Industrial.Core/Transport/ISerialPort.cs` 与 [06 号教程 §5](06-VComPair免驱动工具完全教程.md)。

## 7. 小结

1. 虚拟串口对 = 软件版空调制解调器线，A 写 = B 读。
2. com0com 是内核驱动，生成真正能被所有软件识别的 `COMx`。
3. 默认名 `CNCA0/CNCB0`，改名/放进 Ports 类要靠 `setupc` / `setupg`。
4. 波特率不限速、缓冲不溢出都是默认行为，需要时才用 `EmuBR` / `EmuOverrun` 打开。
5. 最终版本 3.0.0.0（2012），GPLv2，无 Win11 专用版。
6. **只是想把本仓库的串口助手跑通 → 用 VComPair，不用装驱动。**

## 一、C# 基础（1~20）

### 1. 值类型与引用类型有什么区别？★

**答案：** 值类型（`int`、`double`、`bool`、`struct`、`enum`）的变量直接保存数据；引用类型（`class`、`string`、数组、委托）的变量保存对象引用，对象本身在托管堆上。赋值时值类型**复制值**，引用类型**复制引用**，所以两个引用变量可能指向同一个对象。引用类型可以为 `null`，值类型默认不能，除非用 `Nullable<T>`。不要死记“值类型一定在栈上”：它作为对象字段、被闭包捕获或装箱时，数据会跟着对象走。

**背诵骨架：** 存值 / 存引用 → 复制值 / 复制引用 → 可空性 → 栈堆看上下文。

【项目】`TagValue`、`PointConfig` 用 `class`，因为要在采集线程、界面、存储之间共享同一份数据；寄存器原始值用 `ushort` 值类型，解析时复制，不会被别的线程改掉。

---

### 2. `int` 和 `Int32` 是什么关系？

**答案：** 完全是同一个类型。`int` 是 C# 的关键字，`Int32` 是 .NET 基础类库里的类型名，编译后都对应 `System.Int32`，没有任何性能差异。日常代码用 `int` 更符合 C# 习惯；强调跨语言或二进制布局时写 `Int32` 更直观。类似地，`string` 对应 `System.String`，`bool` 对应 `System.Boolean`。

**背诵骨架：** 别名关系，同一个 `System.Int32`，无性能差异。

---

### 3. `const` 和 `readonly` 有什么区别？

**答案：** `const` 是**编译期常量**，值必须在声明时确定，只能是字面量或编译期可算出的表达式，隐式静态，编译时会把值**内联**到调用方；如果改了常量值，引用它的程序集要重新编译。`readonly` 是**运行期只读**，可以在声明时或构造函数里赋值，每个实例可以有不同的值。还要注意：`readonly` 修饰引用类型时，只禁止重新赋值，不禁止修改对象内部状态。

**背诵骨架：** 编译期 vs 运行期；内联 vs 引用；只读引用不等于对象不可变。

【项目】`PollingService` 里的 `MaxRegistersPerRead = 125` 适合 `const`；`CsvHistoryStore` 的目录字段在构造时确定，适合 `readonly`。

---

### 4. `string` 和 `StringBuilder` 有什么区别？

**答案：** `string` 是**不可变**的，每次拼接、替换都会产生新对象，循环里大量拼接会产生很多临时对象和 GC 压力。`StringBuilder` 内部维护可变的字符缓冲区，`Append` 在缓冲区上追加，适合循环拼接或动态生成大文本。少量拼接直接用 `string` 或插值更清楚；`StringBuilder` 不是线程安全的，多线程共享要加锁或每个线程各用一个。合理预设 `Capacity` 可以减少扩容。

**背诵骨架：** 不可变 vs 可变缓冲区；循环拼接用 `StringBuilder`；单线程使用。

【项目】`CsvHistoryStore.SplitCsv` 用 `StringBuilder` 逐字符拼单元格；如果改成用 `string +=`，每行 CSV 都会产生大量临时字符串。

---

### 5. `==` 和 `Equals` 有什么区别？

**答案：** `==` 是**运算符**，在编译期按变量的静态类型解析，可以被重载；`Equals` 是 `object` 的**虚方法**，运行期按实际类型分派，可以被重写。对于 `string`，`==` 和 `Equals` 都做**值比较**；对于普通引用类型，默认 `==` 比较引用，`Equals` 默认也比较引用，但可以重写。重写 `Equals` 时通常要同时重写 `GetHashCode`，否则放进 `Dictionary`/`HashSet` 会出问题。判断引用同一性用 `ReferenceEquals`。

**背诵骨架：** 运算符可重载 vs 虚方法；`string` 值比较；重写 `Equals` 配 `GetHashCode`。

【项目】`HistoryRecord` 是 `record`，编译器自动生成值相等的 `Equals`/`GetHashCode`；`TagValue` 是普通 `class`，默认按引用比较，适合表示“这一条采集结果”。

---

### 6. 什么是装箱和拆箱？

**答案：** **装箱**是把值类型转换成 `object` 或它实现的接口，运行时在堆上分配一个盒子并把值复制进去；**拆箱**是把盒子里的值取出来，必须用**精确的类型**转换，否则抛 `InvalidCastException`。装箱有堆分配和复制成本，频繁装箱会增加 GC。泛型集合（`List<int>`）不会装箱，老的非泛型集合（`ArrayList`）会；把值类型传给 `object` 参数、用 `object` 字典键也可能装箱。

**背诵骨架：** 值类型 → `object` 装箱；拆箱要精确类型；泛型避免。

【项目】协议解析统一用 `ushort[]`、`List<TagValue>` 这类泛型结构，没有用 `ArrayList` 或 `object[]` 存寄存器，避免每个寄存器都装箱。

---

### 7. `ref` 和 `out` 有什么区别？

**答案：** 两者都按**引用**传递，方法内修改会影响调用方。区别是：`ref` 要求调用前必须**已初始化**，方法内可以读也可以写；`out` 调用前可以不初始化，但方法内**必须在返回前赋值**，所以适合“一个返回值不够用”的场景，比如 `int.TryParse`。`out` 参数在方法开头会被视为未赋值，不能先读。现代 C# 可以用 `out var` 就地声明变量。

**背诵骨架：** 都传引用；`ref` 先初始化，`out` 方法内必须赋值；`TryParse`。

【项目】`CsvHistoryStore` 读历史时用 `DateTime.TryParseExact(..., out var ts)` 和 `double.TryParse(..., out var value)`，解析失败不抛异常，直接跳过坏行。

---

### 8. `params` 有什么作用？

**答案：** `params` 让方法接收**可变数量的参数**，编译器把多余实参打包成数组。它必须是参数列表的**最后一个**参数，类型必须是数组；调用时也可以直接传一个数组。每次调用如果传的是散列参数，通常会**新建数组**，热路径上要注意分配。常见于日志、格式化、拼接参数列表。

**背诵骨架：** 可变参数 → 数组；必须放最后；每次调用可能分配数组。

---

### 9. 可空类型 `int?` 是什么？

**答案：** `int?` 是 `Nullable<int>` 的简写，是一个值类型，包含“有没有值”的状态。用 `HasValue` 判断是否有值，`Value` 取值（没有值时会抛 `InvalidOperationException`），`GetValueOrDefault()` 取默认值。它支持提升运算符，比如 `int? a = null; a + 1` 结果仍是 `null`。数据库、配置文件、报警上下限这类“可能没配置”的数值很适合用可空类型。

**背诵骨架：** `Nullable<T>`；`HasValue`/`Value`；`null` 表示“没有值”。

【项目】`PointConfig.LowLimit` 和 `HighLimit` 是 `double?`：`null` 表示这个点位不配报警；`PollingService` 用 `if (point.HighLimit is { } high ...)` 只在配置了上限时才判断。

---

### 10. `??` 和 `?.` 有什么区别？

**答案：** `??` 是**空合并运算符**：左边为 `null` 时返回右边，否则返回左边；`??=` 是“左边为空才赋值”。`?.` 是**空条件运算符**：左边为 `null` 时整个表达式返回 `null`，不会继续访问后面的成员，常用于 `obj?.Property?.Method()`。`?.` 是短路求值，但只解决空引用，不处理业务异常；`!`（null-forgiving）只是告诉编译器“我保证不为空”，运行时不会检查。

**背诵骨架：** `??` 给默认值；`?.` 避免空引用；都短路。

【项目】`SnapshotReady?.Invoke(values)` 和 `DeviceStateChanged?.Invoke(...)` 用 `?.` 防止“没有订阅者”时抛空引用；配置读取用 `??` 给默认值。

---

### 11. `is` 和 `as` 有什么区别？

**答案：** `is` 做**类型判断**，返回 `bool`，不会抛异常；现代写法 `if (obj is TagValue tag)` 还能在判断成功时直接拿到转换后的变量。`as` 做**安全转换**，失败返回 `null`，不抛异常，但只能用于引用类型或可空值类型，不能直接用于 `int` 这类非空值类型。`as` 之后必须判空；如果确定类型，直接用强制转换 `(T)`，失败会抛 `InvalidCastException`，能让错误更早暴露。

**背诵骨架：** `is` 判断；`as` 失败返回 `null`；值类型不能用 `as`。

---

### 12. 什么是字符串驻留？

**答案：** 相同的字符串字面量在运行时会进入**驻留池**，通常共享同一个对象引用，这就是字符串驻留。运行时拼接出来的字符串一般不会自动驻留，可以显式调用 `string.Intern`。由于 `string` 不可变，共享引用是安全的。但不要依赖 `ReferenceEquals` 判断字符串相等，业务比较应该用 `==` 或 `Equals`，它们比较的是字符内容。

**背诵骨架：** 字面量驻留；运行时拼接不驻留；比较用值比较，不用引用比较。

---

### 13. `StringBuilder` 是线程安全的吗？

**答案：** 不是。`StringBuilder` 内部有可变的字符数组和长度状态，多个线程同时 `Append` 可能互相覆盖、长度错乱，甚至抛异常。多线程场景要么给同一个 `StringBuilder` 加锁，要么每个线程各用一个，最后再合并；更高频的日志场景可以用线程安全队列加单线程消费。不要因为“它比 string 快”就在多线程里共享。

**背诵骨架：** 非线程安全；加锁或每线程一个；不要共享。

【项目】`CsvHistoryStore` 的 `SplitCsv` 是单线程局部变量；`Log` 的多线程写入用 `lock (Sync)` 串行化，而不是共享一个 `StringBuilder`。

---

### 14. `Array` 和 `List<T>` 有什么区别？

**答案：** 数组长度**固定**，内存连续，索引访问最快，适合协议缓冲区、定长数据；`List<T>` 是动态数组，内部封装了一个 `T[]`，`Add` 时容量不够会按倍数扩容并复制，支持 `Add/Remove/Insert` 等操作。`List<T>` 有额外的方法调用和容量冗余，不是线程安全的。已知数量时可以在构造时指定 `Capacity`，减少扩容；需要频繁在中间插入删除时，`LinkedList<T>` 或其它结构可能更合适。

**背诵骨架：** 定长 vs 动态；`List` 内部数组扩容；数组用于缓冲区。

【项目】Modbus 读取返回定长的 `ushort[]`；设备点位列表用 `List<PointConfig>`，因为配置数量不固定；`BuildGroups` 也用 `List<RegisterGroup>` 动态收集分组。

---

### 15. `Dictionary` 的原理是什么？

**答案：** `Dictionary<TKey,TValue>` 是**哈希表**：先算 key 的哈希值，映射到桶（bucket），桶里存条目；不同 key 哈希冲突时，.NET 用链式结构（bucket 指向 entries 链）处理。元素增多、负载因子过高时会**扩容并重新哈希**。平均查找是 O(1)，最坏情况可能退化。key 的哈希值必须稳定，所以不要用可变对象做 key；`Dictionary` 不是线程安全的，并发场景用 `ConcurrentDictionary` 或加锁。遍历顺序不保证是插入顺序。

**背诵骨架：** 哈希分桶；冲突链；扩容重哈希；均摊 O(1)；键要稳定。

【项目】`MainForm` 用 `Dictionary<string, TagRow> _tagIndex`，以 `设备名|位号` 为 key 快速定位界面行；配置里的点位仍用 `List<PointConfig>`，因为要按地址排序和遍历。两种结构各司其职。

---

### 16. `IEnumerable` 的延迟执行是什么？

**答案：** `IEnumerable<T>` 本身只是一个“可以遍历”的契约，LINQ 的 `Where`、`Select` 和 `yield return` 通常返回**迭代器**，真正的计算发生在 `foreach`、`ToList`、`Count`、`First` 等枚举时。因此同一个查询枚举两次会执行两次，如果查询里有数据库访问或副作用，结果可能不同、性能也差。需要固定结果时用 `ToList()`/`ToArray()` 物化；只是流式处理则保留延迟执行，避免一次性占内存。`IQueryable` 还会把表达式树翻译成 SQL，和 `IEnumerable` 的内存计算不同。

**背诵骨架：** 延迟执行；枚举时才跑；多次枚举会重跑；要快照就 `ToList`。

【项目】`BuildGroups` 里的 `device.Points.Where(...).OrderBy(...)` 在 `foreach` 时真正执行；`BuildBadSnapshot` 最后调用 `ToList()`，把结果固定下来再抛事件。

### 17. `IDisposable` 有什么用？

**答案：** `IDisposable` 用来**确定性地释放资源**，比如文件句柄、串口、Socket、数据库连接、GDI 对象。这些资源不只是托管内存，GC 不知道什么时候该关，必须由代码在用完时调用 `Dispose`。`using` 语句/声明会编译成 `try/finally`，保证即使抛异常也能释放。实现 `IDisposable` 时通常要提供 `Dispose(bool disposing)` 模式，并在 `Dispose` 里调用 `GC.SuppressFinalize(this)`，避免重复终结。异步释放用 `IAsyncDisposable` 和 `await using`。

**背诵骨架：** 确定性释放；`using` 保证调用；`Dispose` 模式；不要等 GC。

【项目】`IModbusMaster` 继承 `IDisposable`，`ModbusRtuMaster`/`ModbusTcpMaster` 释放串口和 Socket；`PollingService` 实现 `IAsyncDisposable`，`StopAsync` 里取消并等待所有采集循环结束。采集循环用 `using var master = _factory(device)` 保证每台设备的连接最终关闭。

---

### 18. 终结器（析构函数）有什么用？

**答案：** C# 的 `~ClassName()` 是终结器，由 GC 在**不确定的时间**调用，可能在程序退出时都不执行，也不能保证调用顺序。它只适合兜底释放**非托管资源**，而且会延长对象生命周期、增加 GC 压力，甚至阻塞终结器线程。正确做法是实现 `IDisposable`，用 `using` 主动释放；确实需要兜底时用 `SafeHandle` 包装非托管句柄，而不是自己写终结器。`Dispose` 里调用 `GC.SuppressFinalize` 可以避免重复终结。

**背诵骨架：** GC 调用、时间不确定；只兜底非托管；优先 `SafeHandle` + `Dispose`。

---

### 19. `nameof` 有什么用？

**答案：** `nameof(表达式)` 在**编译期**取出标识符的名称字符串，不产生运行时计算。它最大的价值是**重构安全**：改属性名时，`nameof(Property)` 会跟着改，而手写 `"Property"` 不会。常用于 `INotifyPropertyChanged` 的属性名、`ArgumentNullException` 的参数名、日志和异常信息。它只能用于有名字的符号，不能对任意表达式求值。

**背诵骨架：** 编译期取名字；重构安全；零运行时开销。

【项目】`RegisterCodec.Decode` 里抛参数异常时用了 `nameof(registers)`；`TagRow` 的属性变更通知可以用 `nameof(Value)` 代替手写字符串，减少改名漏改。

---

### 20. `record` 和 `class` 有什么区别？

**答案：** `record` 默认是引用类型，但编译器会生成**基于值的相等性**（`Equals`/`GetHashCode`）、`ToString`、`with` 表达式和位置解构，适合 DTO、配置、消息、历史记录这类“靠内容区分”的数据。普通 `class` 默认是**引用相等**，适合有身份、有可变状态的实体。`record` 不是自动不可变：`init` 属性可以在初始化时赋值，普通 `set` 属性仍可修改；需要不可变就用 `init`/构造参数。`record struct` 则是值类型版本。

**背诵骨架：** 值相等 vs 引用相等；`with`；适合数据载体，不适合可变实体。

【项目】`HistoryRecord` 用 `sealed record`，因为它就是一行历史数据，按内容比较合理；`TagValue` 用 `class`，因为它有可变的质量、报警、时间戳，而且界面和采集线程共享同一个对象。

## 二、面向对象与设计（21~30）

### 21. 封装、继承、多态分别是什么？

**答案：** **封装**是把数据和操作数据的方法包在一起，用访问修饰符和属性隐藏实现细节，只暴露稳定的接口；**继承**是子类复用父类的成员，表达“is-a”关系；**多态**是同一个接口或虚方法在不同类型上有不同实现，运行时根据实际对象选择行为。多态的价值是让上层代码只依赖抽象，新增实现时不改调用方。继承会增加耦合，能用组合和接口解决时优先不用继承。

**背诵骨架：** 藏实现、复代码、同接口不同行为。

【项目】上层只依赖 `IModbusMaster`，`ModbusRtuMaster` 和 `ModbusTcpMaster` 各自实现，采集服务不需要知道底层是串口还是 TCP，这就是多态。

---

### 22. 接口和抽象类有什么区别？

**答案：** 接口定义**契约**，一个类可以实现多个接口，接口一般不放实例字段和构造函数；抽象类定义**模板**，一个类只能继承一个抽象类，可以有字段、构造函数、受保护成员和已实现的方法，适合把公共逻辑放在基类、把差异留给子类。选型上看语义：能力用接口（`IDisposable`、`IModbusMaster`），共享实现用抽象基类。接口更容易做 Mock 和替换；抽象类更适合“有共同状态和流程”的继承体系。

**背诵骨架：** 多实现契约 vs 单继承模板；有没有状态和公共实现。

【项目】协议主站用 `IModbusMaster`，因为 RTU 和 TCP 没有多少可共享的状态；如果以后要统一做重试统计、请求计数，可以再加一个抽象基类放公共逻辑。

---

### 23. 重载和重写有什么区别？

**答案：** **重载（overload）** 是同一个类里方法名相同、参数列表不同，编译器在**编译期**根据实参类型和数量选方法，返回类型不同不构成重载。**重写（override）** 是子类重新实现父类的虚方法/抽象方法，方法签名相同，运行期根据实际对象类型**动态分派**。重载是“同名不同参”，重写是“同一签名换实现”，两者解决的问题不同。

**背诵骨架：** 编译期选重载；运行期选重写。

---

### 24. `virtual`、`override`、`new` 有什么区别？

**答案：** `virtual` 表示父类允许子类重写，方法可以有默认实现；`override` 表示子类重写这个虚方法，运行时按实际类型调用；`new` 是**隐藏**父类同名成员，不参与虚方法分派，调用哪个版本取决于变量的**静态类型**。用 `new` 隐藏容易让代码行为反直觉，编译器也会给警告，除非确实要保留旧成员，否则优先用 `override`。`sealed override` 可以重写后禁止再被重写。

**背诵骨架：** `virtual` 允许；`override` 重写；`new` 隐藏看静态类型。

---

### 25. 密封类 `sealed` 有什么用？

**答案：** `sealed` 修饰类表示**不能被继承**，修饰 `override` 方法表示该方法不能再被重写。它的作用一是表达设计意图（这个类不打算作为基类），二是让 JIT 在某些场景做去虚化优化。`string` 就是密封类。不要为了“性能”到处密封；如果类需要被 Mock 或扩展，密封会带来不便，这时优先面向接口设计。

**背诵骨架：** 禁止继承；表达设计意图；可助优化；别乱封。

---

### 26. 为什么说“组合优于继承”？

**答案：** 继承是强耦合的“is-a”关系，父类一改，子类可能全受影响，容易出现“脆弱基类”问题；组合是“has-a”关系，对象通过持有接口/依赖来复用能力，可以在运行时替换，也更容易测试。比如采集服务不需要继承某个通信类，而是持有一个 `IModbusMaster`，换协议只换实现。继承适合真正的类型层次，组合适合能力复用；大多数业务场景组合更灵活。

**背诵骨架：** has-a 优于 is-a；低耦合；避免脆弱基类；运行时可替换。

【项目】`PollingService` 不继承 `ModbusTcpMaster`，而是通过构造函数拿到 `Func<DeviceConfig, IModbusMaster>` 工厂，再持有接口，通信实现可以替换、可以 Mock。

---

### 27. 什么是依赖倒置？

**答案：** 依赖倒置原则（DIP）是说：高层模块不应该依赖低层实现，二者都应该依赖**抽象**；抽象不应该依赖细节，细节应该依赖抽象。落地方式通常是面向接口编程 + 构造函数注入，高层不自己 `new` 低层对象。这样替换实现、写单元测试、做 Mock 都更容易。依赖注入（DI）是实现 DIP 的一种手段，但不等于必须上 DI 容器。

**背诵骨架：** 依赖抽象；构造注入；上层不 `new` 下层。

【项目】`PollingService` 依赖 `IModbusMaster` 和工厂委托，不直接 `new ModbusTcpMaster`；具体创建交给 `ModbusMasterFactory`，采集逻辑和协议实现解耦。

---

### 28. 单例模式怎么写？有什么缺点？

**答案：** 单例保证一个类只有一个实例，并提供全局访问点。基本写法是私有构造函数 + 静态实例 + 静态获取方法；多线程下要保证只创建一次，推荐 `Lazy<T>`（默认线程安全），或者双重检查锁 + `volatile`。缺点是全局状态、隐藏依赖、难测试、难并行，滥用会让模块之间偷偷耦合。现代项目更推荐把对象注册为 DI 容器的 Singleton 生命周期，而不是自己写单例。

**背诵骨架：** 私构造 + 静态实例 + 线程安全；全局状态慎用；DI Singleton 优先。

【项目】`Log` 是静态工具类，效果类似全局单例，胜在简单、任何地方都能记日志；代价是测试时不好替换，正式项目可以注入 `ILogger`。

```csharp
public sealed class Singleton
{
    private static readonly Lazy<Singleton> _instance =
        new(() => new Singleton(), LazyThreadSafetyMode.ExecutionAndPublication);

    public static Singleton Instance => _instance.Value;

    private Singleton() { }
}
```

---

### 29. 工厂模式解决什么问题？

**答案：** 工厂模式把**对象的创建**从使用方抽离出来，使用方只依赖接口，工厂根据配置或参数决定创建哪个具体类。好处是新增实现时只改工厂或注册表，调用方不动；创建逻辑（读配置、设参数、选协议）集中在一处，避免散落。常见形式有简单工厂（一个 `switch`）、工厂方法和抽象工厂。简单场景用一个静态工厂方法就够了，不必上复杂的工厂体系。

**背诵骨架：** 按配置造对象；集中 `new`；上层只认接口；新增实现少改调用方。

【项目】`ModbusMasterFactory.Create(DeviceConfig)` 根据 `DeviceProtocol` 返回 TCP 或 RTU 主站，`PollingService` 只拿到 `IModbusMaster`。新增协议时主要改工厂和实现类。

```csharp
return device.Protocol switch
{
    DeviceProtocol.ModbusTcp => new ModbusTcpMaster(device.Host, device.Port, timeoutMs),
    DeviceProtocol.ModbusRtu => CreateRtu(device, timeoutMs, enableDtrRts),
    _ => throw new NotSupportedException($"不支持的协议：{device.Protocol}")
};
```

---

### 30. 策略模式解决什么问题？

**答案：** 策略模式把一组可互换的算法封装成独立类，统一实现一个接口，上下文持有这个接口并在运行时选择具体策略。它适合替代又长又稳定的 `if/else` 或 `switch`，比如不同的报警判定、不同的重试策略、不同的协议编解码。新增策略时只加类，不改上下文，符合开闭原则。代价是类数量增加，只有两三个简单分支时没必要硬套。

**背诵骨架：** 算法抽接口；运行时可换；替代大 `if`；别过度设计。

【项目】现在报警判定是 `PollingService.Decode` 里的两行 `if`，点位少时够用；如果以后要支持变化率报警、持续时间报警、分级报警，就抽成 `IAlarmRule` 策略，配置里为每个点位选规则。

## 三、WinForms / WPF / MVVM（31~45）

### 31. 如何跨线程更新 WinForms 界面？★

**答案：** WinForms 控件有**线程亲和性**，只有创建它的 UI 线程能直接访问；后台线程直接改控件会抛 `InvalidOperationException`（跨线程操作无效）。正确做法是把更新封送到 UI 线程：WinForms 用 `Control.Invoke`（同步）或 `BeginInvoke`（异步），WPF 用 `Dispatcher.Invoke/BeginInvoke`。先判断 `IsHandleCreated`/`IsDisposed`，窗口关闭后不要再投递。高频采集不要每个点都 `Invoke` 一次，应该按批次合并刷新，否则 UI 线程会被消息淹没。

**背诵骨架：** 控件有线程亲和 → `BeginInvoke` 回 UI → 批量刷新 → 关闭后停投递。

【项目】`PollingService.SnapshotReady` 在后台线程触发，`MainForm.OnSnapshotReady` 先判断窗口状态，再用 `BeginInvoke(new Action<IReadOnlyList<TagValue>>(ApplySnapshot), values)` 把整批快照交给 UI 线程，而不是每个点位单独更新。

---

### 32. `Invoke` 和 `BeginInvoke` 有什么区别？

**答案：** `Invoke` 是**同步**的：把委托投递到 UI 线程后，调用线程会阻塞，直到 UI 线程执行完才返回；如果 UI 线程正在等调用线程，就会死锁。`BeginInvoke` 是**异步**的：投递后立即返回，UI 线程稍后执行，适合高频、不需要等结果的刷新。两者都要求控件句柄已经创建，窗口销毁后调用会抛异常。后台线程更新界面通常优先 `BeginInvoke`；需要拿到 UI 计算结果时才用 `Invoke`，并注意死锁。

**背诵骨架：** 同步等待 vs 异步投递；高频用 `BeginInvoke`；注意句柄和死锁。

【项目】采集刷新用 `BeginInvoke`，不阻塞采集循环；如果窗口已经关闭，`BeginInvoke` 会抛 `InvalidOperationException`，代码里捕获并忽略。

---

### 33. 界面卡顿通常是什么原因？

**答案：** 最常见是 **UI 线程被阻塞**：同步 IO、`Thread.Sleep`、`.Result`/`.Wait()`、长时间计算、弹模态框。其次是**刷新太频繁**：每个采集点都更新一次表格/图表，消息队列处理不过来；还有**布局和重绘太重**：大量控件、自动列宽、复杂样式、没有双缓冲；以及**数据量太大**：一次性绑定几万行。排查时先看 CPU 和 UI 线程栈，再分别用异步化、批量刷新、虚拟化、双缓冲、限制图表点数来解决。

**背诵骨架：** UI 线程被堵；刷新过频；布局太重；数据太大。

【项目】采集在后台 `Task` 里跑，UI 只接收快照；趋势图限制 1500 个点，超出就丢最旧的；但如果点位特别多，还需要把 `BeginInvoke` 改成定时批量刷新。

---

### 34. 双缓冲有什么用？怎么开？

**答案：** 双缓冲让绘制先发生在**离屏缓冲区**，画完再一次性复制到屏幕，避免逐笔绘制时闪烁。WinForms 自绘控件可以在构造函数里设置 `SetStyle(ControlStyles.AllPaintingInWmPaint | ControlStyles.UserPaint | ControlStyles.OptimizedDoubleBuffer, true)`，也可以设 `DoubleBuffered = true`；`DataGridView` 的双缓冲是受保护的，需要子类化或反射开启。双缓冲只解决闪烁，不解决“画得太慢”；点太多、每帧全量重绘仍然会卡。WPF 本身是保留模式合成，通常不需要手动双缓冲。

**背诵骨架：** 离屏画完再拷贝；防闪烁；不解决绘制慢。

【项目】`TrendChart` 是 WinForms 自绘控件，构造函数里开启了 `AllPaintingInWmPaint | OptimizedDoubleBuffer`，同时把点数限制在 1500，避免每帧重绘过多。

---

### 35. `Dock` 和 `Anchor` 有什么区别？

**答案：** `Dock` 让控件**贴边或填满**父容器，可以取 Top/Bottom/Left/Right/Fill；多个 Dock 控件有顺序（取决于控件在集合中的顺序），Fill 会占据剩余空间。`Anchor` 让控件与父容器某几条边保持**固定距离**，窗口缩放时按锚点调整位置和大小。简单布局用 Dock/Anchor，复杂布局用 `TableLayoutPanel` 或 `FlowLayoutPanel`，否则控件重叠、顺序错乱很难调。高 DPI 下还要注意 AutoScaleMode 和字体缩放。

**背诵骨架：** 贴边 vs 相对锚定；Dock 有顺序；复杂布局用 TableLayoutPanel。

---

### 36. DataGridView 显示大量数据怎么优化？

**答案：** 数据量大时不要一次性绑定完整列表。用 **VirtualMode**，只提供当前可见行，通过 `CellValueNeeded` 按需取数；关闭 `AutoSizeColumnsMode`（自动列宽会遍历所有行），固定列宽；开启双缓冲、`SuspendLayout`/`ResumeLayout` 批量更新；避免逐单元格设置样式；分页或按时间范围查询。`BindingList` 适合几百上千行、需要增删通知的场景；几万行以上应该虚拟化或分页。

**背诵骨架：** VirtualMode；关自动列宽；批量刷新；分页。

【项目】实时点位表用 `BindingList<TagRow>`，因为点位数量不大、需要增删和属性通知；历史查询如果返回几万行，就不应该直接塞进 `DataGridView`，而要用分页或 VirtualMode。

---

### 37. `BindingList` 有什么用？

**答案：** `BindingList<T>` 实现了 `IBindingList`，在集合增删、重置时触发 `ListChanged`，绑定到 `DataGridView` 后界面会自动增删行。注意：元素**属性变化**不会自动通知，元素类型还要实现 `INotifyPropertyChanged`，否则改了 `Value` 界面不刷新。`BindingList` 不是线程安全的，后台线程修改要切回 UI 线程；需要排序/筛选时可以套一层 `BindingSource`。WPF 对应的是 `ObservableCollection<T>`。

**背诵骨架：** 集合变更通知；元素属性要 `INotifyPropertyChanged`；非线程安全。

【项目】`MainForm` 用 `BindingList<TagRow>` 存实时点位、`BindingList<AlarmRecord>` 存报警；`TagRow` 实现了 `INotifyPropertyChanged`，所以后台改 `Value`、`Quality` 后表格能刷新。采集回调仍然通过 `BeginInvoke` 回到 UI 线程再改集合。

---

### 38. WPF 绑定不刷新，通常是什么原因？

**答案：** 先查四件事：**通知**——属性有没有实现 `INotifyPropertyChanged` 并在 setter 里触发 `PropertyChanged`，集合有没有用 `ObservableCollection`；**上下文**——`DataContext` 是否为空或设错，绑定路径是否能解析；**模式**——`Mode=OneTime` 只读一次，`OneWay` 不会从界面回写；**线程**——后台线程改绑定源可能不刷新或抛异常。再查属性是否是 `public`、路径大小写、转换器是否报错。调试时看 Visual Studio 的 Output 窗口，WPF 会打印绑定错误；也可以用 Snoop 查可视化树。

**背诵骨架：** 没通知 / 没上下文 / 模式不对 / 线程不对。

【项目】`ScadaDashboard` 的 `ObservableObject` 实现了 `INotifyPropertyChanged`，`TagViewModel` 继承它；`MainWindow` 构造时把 `DataContext` 设为 `MainViewModel`，绑定路径和通知都能对上。

---

### 39. WPF 的 `DataContext` 是什么？

**答案：** `DataContext` 是 WPF 绑定的**默认数据源**，会沿着可视化树向下继承；子元素没有显式设置时，会拿到最近的祖先的 `DataContext`。通常把 ViewModel 赋给窗口的 `DataContext`，界面里的 `{Binding Name}` 就会去 ViewModel 上找 `Name`。可以用 `Source`、`ElementName`、`RelativeSource` 覆盖默认源；`ItemsControl` 里每一项的 `DataContext` 会变成该数据项。绑定不生效时，`DataContext` 为空是最常见的原因之一。

**背诵骨架：** 默认绑定源；沿可视化树继承；可被局部覆盖。

【项目】`MainWindow.xaml.cs` 里 `DataContext = new MainViewModel()`，XAML 里的 `{Binding StartCommand}`、`{Binding Tags}` 都落到这个 ViewModel 上。

---

### 40. `DataTemplate` 和 `ControlTemplate` 有什么区别？

**答案：** `DataTemplate` 描述**数据对象长什么样**，比如列表里每个 `TagViewModel` 显示成一张卡片，常用 `ItemTemplate`、`ContentTemplate`；它拿到的是数据对象，内部用普通 `Binding`。`ControlTemplate` 描述**控件本身的结构和状态**，比如按钮由哪些元素组成、按下/禁用时怎么变，常用 `Template`；内部用 `TemplateBinding` 或 `RelativeSource TemplatedParent` 绑定到控件属性。简单说：一个是“数据的外观”，一个是“控件的外观”。

**背诵骨架：** 数据长什么样 vs 控件长什么样；`ItemTemplate` vs `Template`；`Binding` vs `TemplateBinding`。

【项目】`ScadaDashboard` 的 `ListBox.ItemTemplate` 用 `DataTemplate` 把每个点位渲染成带名称、数值、单位的卡片，并通过 `DataTemplate.Triggers` 根据报警状态改颜色。

---

### 41. `ICommand` 有什么用？

**答案：** `ICommand` 把“用户操作”抽象成对象，包含 `Execute`（执行）和 `CanExecute`（能否执行），`CanExecuteChanged` 通知界面刷新按钮可用状态。这样 View 只负责绑定命令，业务逻辑放在 ViewModel，按钮和逻辑解耦，也方便测试。常用 `RelayCommand`/`DelegateCommand` 实现；异步命令要加 `IsExecuting` 防重入，并在执行期间禁用按钮。`CanExecute` 返回 `false` 时按钮会自动变灰。

**背诵骨架：** 执行 + 能否执行；解耦按钮与逻辑；异步防重入。

【项目】`ScadaDashboard` 用 `RelayCommand` 实现 `StartCommand`、`StopCommand`、`ClearAlarmsCommand`；XAML 里按钮只写 `Command="{Binding StartCommand}"`，没有一行 `Click` 事件代码。

---

### 42. MVVM 有什么优缺点？

**答案：** 优点是**关注点分离**：View 只管布局和样式，ViewModel 管状态和命令，Model 管数据；ViewModel 不依赖控件，容易单元测试；UI 改版时业务逻辑不动；设计师和开发可以并行。缺点是学习和调试成本高：绑定错误不报编译错误、命令和通知样板代码多、简单页面强行 MVVM 会过度设计。实际项目里可以混合：复杂页面用 MVVM，简单的对话框用 code-behind 更直接，不必教条。

**背诵骨架：** 解耦、可测、可换 UI vs 学习成本、绑定难调、简单页面过度设计。

【项目】`ScadaDashboard` 的 ViewModel 里没有 `Dispatcher`、没有控件类型，采集和命令都在 VM；`MainWindow.xaml.cs` 只负责挂 `DataContext` 和把趋势图这种纯 UI 动作接上。

---

### 43. 什么是依赖属性？

**答案：** 依赖属性（DependencyProperty）是 WPF 的属性系统：属性值不是存在普通字段里，而是由 WPF 统一管理，支持**数据绑定、样式、触发器、动画、属性值继承、默认值**。定义时用 `DependencyProperty.Register` 注册，再提供一个 CLR 包装属性（`GetValue`/`SetValue`）。依赖属性通常用在自定义控件、需要被 XAML 绑定或样式化的属性上；普通 ViewModel 属性用 `INotifyPropertyChanged` 就够了，不需要都做成依赖属性。附加属性是一种特殊的依赖属性。

**背诵骨架：** WPF 属性系统；绑定/样式/动画/继承；`Register` + CLR 包装。

【项目】`TrendChartControl` 目前用普通 CLR 属性接收数据，由 `MainWindow` 直接调用；如果要做成可复用的图表控件、支持 XAML 绑定和样式，应该把标题、单位、上下限等改成依赖属性。

---

### 44. WPF 是怎么渲染的？

**答案：** WPF 基于 **DirectX**，采用保留模式：先构建可视化树，布局阶段做 Measure/Arrange，渲染阶段由 WPF 合成；自定义绘制可以重写 `OnRender(DrawingContext dc)`，WPF 会把绘制指令保留下来，需要时重绘。它和 WinForms 的 GDI 立即模式不同，矢量图形缩放更清晰，动画和特效更容易。性能上要避免每帧创建大量几何对象、频繁 `InvalidateVisual`；点太多时应该降采样或分层绘制。

**背诵骨架：** DirectX + 保留模式；Measure/Arrange/Render；`OnRender`；避免每帧重绘。

【项目】`TrendChartControl` 重写 `OnRender`，用 `DrawingContext` 画坐标轴、网格和折线；点数限制 1500，选中点位变化时才重置，避免无意义的重绘。

---

### 45. WinForms 和 WPF 怎么选？

**答案：** WinForms 成熟、拖控件快、工业现场存量项目多、第三方工控控件丰富，适合业务表单、设备调试工具、交付周期短的项目；缺点是布局和 DPI 适配弱、样式老、复杂动画和自定义 UI 费劲。WPF 矢量渲染、样式/模板/绑定/MVVM 更强，适合新项目、复杂看板、需要高 DPI 和现代化 UI 的场景；代价是学习曲线、绑定调试和性能坑。选型看团队、存量代码、交付周期和客户环境，不是“WPF 一定比 WinForms 高级”。

**背诵骨架：** 存量/快速/工控控件 vs 新项目/复杂 UI/高 DPI；看团队和交付。

【项目】串口助手和 ModbusMonitor 用 WinForms，因为表单密集、上手快、现场机器兼容性好；ScadaDashboard 用 WPF + MVVM，练习绑定、命令和自绘看板。两个都做，是为了能接不同类型的项目。

## 四、多线程与异步（46~60）

### 46. 进程和线程有什么区别？

**答案：** 进程是**资源分配**的基本单位，有独立的虚拟地址空间、句柄表和权限；线程是 **CPU 调度**的基本单位，同一进程内的线程共享堆、静态变量和文件句柄，但各自有栈和寄存器。进程之间隔离性好，一个进程崩溃通常不影响另一个；线程之间共享内存，通信快，但必须自己做同步，否则会出现竞态、死锁。线程切换有上下文切换成本，线程不是越多越好。

**背诵骨架：** 资源分配 vs 调度；隔离 vs 共享；共享就要同步。

【项目】整个上位机是一个进程，每台设备一个采集循环（`Task`）；它们共享配置和日志，但每台设备的通信对象、寄存器缓冲各自独立，减少锁竞争。

---

### 47. 前台线程和后台线程有什么区别？

**答案：** **前台线程**会阻止进程退出：只要还有一个前台线程在跑，进程就不会结束；**后台线程**不会阻止进程退出，主线程结束时后台线程会被直接终止。可以通过 `Thread.IsBackground` 设置；线程池线程和 `Task` 默认是后台线程。上位机的采集线程应该能**优雅停止**，不能依赖“进程退出时被强杀”，否则可能丢数据、留半截文件。退出前要取消令牌、等待循环结束、释放串口和文件。

**背诵骨架：** 前台阻止退出；后台不阻止；线程池是后台；退出要优雅。

【项目】`PollingService` 用 `Task.Run` 启动采集循环，属于后台线程；关窗时调用 `StopAsync` 取消并等待，而不是靠进程退出直接终止。

---

### 48. `Task` 和 `Thread` 有什么区别？

**答案：** `Thread` 是**专用的操作系统线程**，创建、启动、`Join` 都要手动管理，开销较大；`Task` 是更高层的抽象，默认跑在**线程池**上，支持延续、组合（`WhenAll`/`WhenAny`）、取消和异常聚合。CPU 密集型工作用 `Task.Run`；I/O 密集型工作用真正的异步 API（`ReadAsync`、`WriteAsync`），不要用 `Task.Run` 包一个阻塞 IO 来假装异步。需要长期独占线程的场景（比如某些阻塞串口读）可以用 `TaskCreationOptions.LongRunning` 或专用线程。

**背诵骨架：** 专用线程 vs 线程池任务；组合/取消/异常；IO 用真异步。

【项目】TCP 采集用 `NetworkStream.ReadAsync`，是真正的异步 IO；RTU 的串口读写是阻塞的，目前用 `Task.Run` 包住，设备很多时会占用线程池线程，这是一个可以继续优化的点。

---

### 49. `async/await` 的原理是什么？★

**答案：** `async` 方法会被编译器改写成**状态机**：遇到 `await` 时，如果任务还没完成，方法先返回一个 `Task` 给调用方，把后续代码注册为延续；任务完成后，再恢复状态机继续执行。`await` **不会阻塞线程**，也不一定创建新线程；I/O 异步靠操作系统完成通知，CPU 密集型才需要 `Task.Run` 丢到线程池。异常会被捕获到返回的 `Task` 里，`await` 时重新抛出。`async void` 只适合事件处理器，因为调用方无法等待、异常会直接冲到同步上下文。

**背诵骨架：** 状态机；`await` 让出线程；完成后延续；异常在 `Task` 里。

【项目】`PollLoopAsync` 是 `async` 循环：`await ReadHoldingRegistersAsync` 时线程可以去做别的事，读完后继续解析；库代码统一用 `ConfigureAwait(false)`，不依赖 UI 上下文。

---

### 50. 为什么 `.Result` 或 `.Wait()` 容易死锁？★

**答案：** 经典场景：UI 线程调用 `SomeAsync().Result`，同步阻塞等待任务完成；而 `SomeAsync` 内部的 `await` 默认要捕获 UI 的 `SynchronizationContext`，任务完成后需要把延续**投递回 UI 线程**执行；但 UI 线程正卡在 `.Result` 上，永远没机会执行延续，于是互相等待，死锁。修复方式是**全链路 async/await**，不要在 UI 线程同步等待；库代码用 `ConfigureAwait(false)` 减少捕获上下文，但这不能治愈 UI 层的阻塞。`Task.Run(...).Result` 也可能因为内部继续回 UI 而死锁。

**背诵骨架：** UI 阻塞 + 延续要回 UI = 死锁；全链路 `async`；别用 `.Result`/`.Wait`。

【项目】采集和通信全部在后台任务里，UI 线程不调用 `.Result`；快照通过 `BeginInvoke` 投递。WPF 关窗时有一个 1.5 秒的有限等待，严格说应该改成异步关闭，避免关窗时短暂卡顿。

---

### 51. `ConfigureAwait(false)` 有什么用？

**答案：** `await` 默认会捕获当前的 `SynchronizationContext` 或 `TaskScheduler`，任务完成后把延续调度回原上下文；`ConfigureAwait(false)` 表示**不捕获上下文**，延续直接在线程池上执行。类库/核心逻辑应该用 `false`，避免依赖调用方的 UI 上下文，减少死锁风险，也略省一点调度开销；UI 层在 `await` 之后还要操作控件时，不能随便用 `false`，否则可能不在 UI 线程。它不是“性能银弹”，也不能修复同步阻塞。

**背诵骨架：** 库代码不捕获上下文；UI 代码要上下文；不治 `.Result`。

【项目】`Industrial.Core` 里的 `PollingService`、`ModbusTcpMaster`、`ModbusRtuMaster` 基本每个 `await` 都加了 `ConfigureAwait(false)`；UI 项目里不这样写，因为更新控件需要回到 UI 线程。

---

### 52. `lock` 锁的到底是什么？

**答案：** `lock (obj)` 锁的是**引用对象**上的监视器（Monitor），不是锁代码块，也不是锁变量本身。多个线程必须锁**同一个对象实例**才互斥；锁值类型会装箱，每次都是新对象，等于没锁。不要锁 `this`、`string`、`typeof(...)` 或公开对象，容易和外部代码意外竞争。锁对象应该是 `private static readonly object`（实例锁用 `private readonly object`）。`lock` 可重入，临界区要短，**不要在里面 `await`**，也不要在锁里调用可能回调外部代码的方法。

**背诵骨架：** 锁引用对象；私有 readonly；同一实例才互斥；短临界区；别 `await`。

【项目】`CsvHistoryStore` 用 `private readonly object _sync` 串行化文件和内存操作；`Log` 用 `lock (Sync)` 防止多线程写日志交错；`ModbusRtuMaster` 用 `lock (_sync)` 保护一次完整的串口事务。

---

### 53. `Interlocked` 有什么用？

**答案：** `Interlocked` 提供**原子操作**，比如 `Increment`、`Decrement`、`Add`、`Exchange`、`CompareExchange`，底层依赖 CPU 原子指令，不需要显式加锁。它适合计数器、状态标志、无锁更新引用；`CompareExchange` 可以实现乐观并发。注意它只保证**单个操作**原子，多个步骤组合仍需要锁或其它同步；`long`/`double` 在 32 位平台上的读写也不一定原子，`Interlocked` 能提供帮助。它比 `lock` 轻，但不是所有场景都能替代锁。

**背诵骨架：** 原子加减/交换；计数器；只保单步；不是万能锁。

【项目】采集统计里的“成功次数/失败次数”可以用 `Interlocked.Increment`，避免为了两个计数器加一把锁；当前项目量小，用普通字段加日志也能接受。

---

### 54. `volatile` 有什么用？

**答案：** `volatile` 保证字段读写的**可见性**和一定的**禁止重排**：一个线程写入后，另一个线程能及时看到新值，编译器/CPU 不会把访问随意重排到屏障另一侧。但它**不保证原子性**，`count++` 这种“读-改-写”仍然会丢更新；它也不能用于 `long`/`double`，64 位值的读写也不一定原子。它只适合简单的停止标志、状态标志；更稳的做法是用 `CancellationToken`、`Interlocked` 或 `lock`。不要以为加了 `volatile` 就线程安全。

**背诵骨架：** 可见性；不保证原子；只适合简单标志；优先取消令牌/`Interlocked`。

【项目】采集循环的停止不用 `volatile bool`，而是用 `CancellationToken`，因为它还能让 `Task.Delay`、`ReadAsync` 等操作一起取消，语义更完整。

---

### 55. `ConcurrentQueue` 有什么用？

**答案：** `ConcurrentQueue<T>` 是线程安全的 FIFO 队列，支持多线程同时 `Enqueue`/`TryDequeue`，内部用无锁/细粒度同步实现，适合生产者-消费者缓冲。它不会阻塞等待：队列空时 `TryDequeue` 返回 `false`，需要等待就用 `BlockingCollection`、`Channel` 或信号量。`Count` 在并发下只是一个近似快照，不适合做精确同步；遍历也是快照语义。它适合“采集线程生产、UI/存储线程消费”的解耦。

**背诵骨架：** 线程安全队列；生产者消费者；不阻塞等待；等待用 `BlockingCollection`/`Channel`。

【项目】历史记录就是生产者-消费者：采集回调 `_history.Enqueue(...)` 入 `ConcurrentQueue`，WinForms 定时器 `tmrFlush` 每秒调 `FlushHistory`，一次最多取 5000 条交给 `CsvHistoryStore.Append`。UI 刷新仍用 `BeginInvoke`；如果点位再多，可以把快照也改成队列批量刷新。

---

### 56. 定时器为什么会重入？怎么避免？★

**答案：** `System.Threading.Timer`、`System.Timers.Timer` 的回调是在线程池上执行的，如果上一次回调还没跑完，下一次时间又到了，就可能**并发重入**，导致同一份数据被重复处理、锁竞争甚至错乱。避免方法：用 `Interlocked` 标志/`SemaphoreSlim` 保证单次执行；回调里先停表、处理完再开；或者干脆不用定时器，用一个 `while` 循环 + `Task.Delay` 串行执行。UI 定时器（`System.Windows.Forms.Timer`）回调在 UI 线程，不会并发重入，但长时间处理仍会卡界面。

**背诵骨架：** 上次没完又触发；标志/停表/单循环；UI 定时器不重入但会卡。

【项目】`PollingService` 没有用定时器，而是每台设备一个 `while` 循环：记录 `Stopwatch`，读完再算剩余时间 `Task.Delay`，天然不会重入，也能保证“上一轮读完再开始下一轮”。

---

### 57. 如何优雅地停止后台线程？

**答案：** 用 `CancellationTokenSource` 统一发取消信号，把 `Token` 传给所有异步操作和循环；循环里检查 `IsCancellationRequested`，`Task.Delay`/`ReadAsync` 等接受 token 的操作会抛 `OperationCanceledException`，捕获后正常退出。停止方调用 `Cancel()`，然后 `await Task.WhenAll(tasks)` 等待所有循环结束，最好加一个超时兜底；最后释放串口、文件、定时器等资源。不要用 `Thread.Abort`（可能损坏状态），也不要只把线程设成后台线程就撒手不管。

**背诵骨架：** 取消令牌 → 等待全部结束 → 释放资源；别 `Thread.Abort`。

【项目】`PollingService.StopAsync` 先 `cts.Cancel()`，再 `await Task.WhenAll(_loops)`，最后 `Dispose`；每个循环里的 `Task.Delay` 和通信都接收 token，所以能及时退出。关窗时 UI 用 1.5 秒有限等待兜底，避免进程残留。

---

### 58. 什么是线程池饥饿？

**答案：** 线程池的线程数量有限，如果大量任务都在**同步阻塞**（`Thread.Sleep`、`.Result`、同步 IO、等锁），线程被占满，后面的任务只能排队，表现为“什么都没干但很慢”，这就是线程池饥饿。根因通常是 sync-over-async 或把长阻塞任务丢进线程池。解决：I/O 用真正的异步 API；长阻塞任务用专用线程或 `LongRunning`；避免在热路径上 `.Result`/`.Wait`；`ThreadPool.SetMinThreads` 只能缓解、不能根治，而且线程太多会增加切换成本。

**背诵骨架：** 阻塞任务占满线程池；异步 IO / 专用线程；别 sync-over-async。

【项目】TCP 用异步 IO，不占线程；RTU 串口读是阻塞的，用 `Task.Run` 包住会占一个线程池线程，设备数量大时要改成每台设备专用线程或异步串口封装。这是我在项目里明确知道的取舍。

---

### 59. 死锁的四个必要条件是什么？

**答案：** 互斥、占有并等待、不可抢占、循环等待。只要破坏其中一个就能避免死锁：锁按固定顺序获取（破坏循环等待）、用 `TryEnter`/超时（破坏无限等待）、尽量缩小锁范围、避免嵌套锁、一次性申请所需资源。异步场景还有另一种“上下文死锁”：UI 线程同步等待一个需要回 UI 的任务，本质是等待环。排查时看线程栈里谁持有什么锁、在等谁。

**背诵骨架：** 互斥/占有/不可抢占/循环等待；破一个；锁顺序/超时/少嵌套。

【项目】`PollingService` 每台设备一个独立主站，设备之间不共享锁；`CsvHistoryStore` 只有一把文件锁；没有“持 A 锁等 B 锁”的嵌套，降低了死锁概率。

---

### 60. 程序卡死时怎么排查？

**答案：** 先确认是**真死锁**、**死循环**还是**卡在 IO**。抓 dump（任务管理器“创建转储文件”、ProcDump、`dotnet-dump`），用 WinDbg/Visual Studio 看所有线程的调用栈，重点看 UI 线程在等什么、有没有线程持有锁又在等另一把锁。同时查日志最后一条、性能计数器（CPU、线程数、GC、句柄）、Windows 事件查看器。能复现就加日志缩小范围；不要第一反应就重启，重启会丢掉现场。托管程序还可以用 `dotnet-stack` 快速看栈。

**背诵骨架：** 抓 dump 看栈；日志定位最后动作；查锁/IO/GC；先保现场。

【项目】现场排查时先看 `logs/yyyyMMdd.log` 里最后一帧通信和设备状态，再判断是串口超时、网络断开还是 UI 线程被阻塞；协议层有超时异常，不会无限等。

## 五、工业通信与 Modbus（61~80）

### 61. RS232 和 RS485 有什么区别？★

**答案：** RS232 是**单端信号**，靠 TX/RX 对地电压传数据，通常**点对点**、全双工，距离十几米，抗干扰弱；RS485 是**差分信号**，靠 A/B 两线电压差传数据，支持**多点总线**、半双工，距离可达 1200 米，抗干扰强。485 总线上多个从站要按站号轮询，同一时刻只能一个主站发问；总线两端要终端电阻，线要用双绞线，必要时加隔离。现场说“232 转 485”就是加一个转换器，把单端信号变成差分信号。

**背诵骨架：** 单端/差分；点对点/总线；全双工/半双工；15 米/1200 米。

【项目】Modbus RTU 跑在 485 上，配置里要设 `COM` 口、波特率、数据位、校验、停止位和从站号；半双工意味着一问一答，不能多个线程同时发。

---

### 62. 485 总线的终端电阻有什么用？

**答案：** 终端电阻用于**阻抗匹配**，吸收信号到达电缆末端时的反射，减少波形振铃和误码。标准做法是在总线**最远的两端**各接一个 120Ω 电阻，中间节点不接；短线、低波特率时可能不接也能跑，但长线或高波特率下反射会明显。除了终端电阻，有时还需要**偏置电阻**保证空闲时 A/B 有确定电平，避免收到乱码。总线要**手拉手**串接，避免星形分支和长支线；屏蔽层接地方式要看现场，接地不当反而引入干扰。

**背诵骨架：** 两端 120Ω；阻抗匹配；手拉手；偏置/接地看现场。

---

### 63. 串口参数 9600-8-N-1 分别是什么？★

**答案：** 9600 是**波特率**，每秒约 9600 个信号位；8 是**数据位**，一个字符 8 位；N 是**无校验**（None），也可以选奇校验/偶校验；1 是**1 位停止位**。此外还有起始位，所以 8N1 实际每字节占 10 位，9600 下理论约 960 字节/秒。通信双方这些参数**必须完全一致**，否则收到乱码或 CRC 错。工业现场 8E1（偶校验）也常见，校验位能帮助发现传输错误，但不能纠错。

**背诵骨架：** 波特率/数据位/校验/停止位；两端一致；8N1 每字节 10 位。

【项目】`DeviceConfig` 默认 9600、8 数据位、无校验、1 停止位；`SerialSettings` 把这些参数传给串口封装，任何一项和仪表不一致都连不上。

### 64. TCP 的粘包和半包是什么？怎么处理？★

**答案：** TCP 是**字节流**，没有消息边界：一次 `Read` 可能读到半帧，也可能读到一帧半甚至多帧，这就是半包/粘包。处理方式是在应用层**自己定界**：固定长度、长度字段（包头里写后续字节数）、分隔符，或者像 Modbus RTU 那样靠静默时间分帧。接收端要维护一个缓冲区，循环解析：够一帧就取出处理，不够就把剩余字节留在缓冲区，等下次数据拼接。不能假设“一次 `Read` 就是一帧”，也不能把没解析完的字节丢掉。

**背诵骨架：** 字节流无边界；长度/分隔符/固定长度定界；缓冲区留残包。

【项目】Modbus TCP 先读 7 字节 MBAP 头，从长度字段算出后续字节数，再 `ReadExactAsync` 读满；Modbus RTU 先读 3 字节头（站号、功能码、后续长度信息），按功能码推算总长度，再读剩余字节并校验 CRC。两边都不是“读一次就当一帧”。

### 65. 手写 Modbus CRC16。★

**答案：** Modbus RTU 用 CRC16，多项式是 `0xA001`（`0x8005` 的反转），初值 `0xFFFF`，每个字节先和 CRC 异或，再做 8 次右移；如果最低位是 1，就异或 `0xA001`。算出的 CRC **低字节先发**。它只能检错、不能纠错；校验范围是从站地址到数据最后一个字节，不包括 CRC 本身。

```csharp
public static ushort Compute(ReadOnlySpan<byte> data)
{
    ushort crc = 0xFFFF;
    foreach (var b in data)
    {
        crc ^= b;
        for (var i = 0; i < 8; i++)
        {
            if ((crc & 0x0001) != 0)
                crc = (ushort)((crc >> 1) ^ 0xA001);
            else
                crc >>= 1;
        }
    }
    return crc;
}

// 发送：低字节在前
frame[^2] = (byte)(crc & 0xFF);
frame[^1] = (byte)(crc >> 8);
```

**背诵骨架：** 初值 `FFFF`、多项式 `A001`、异或后 8 次移位、低字节先发。

【项目】`Industrial.Core/Modbus/Crc16.cs` 就是这段实现；`SelfCheck` 用标准向量 `01 03 00 00 00 0A` 验证，CRC 应为 `CDC5`，发送顺序是 `C5 CD`，篡改任意字节后校验必须失败。

### 66. Modbus RTU 的一帧长什么样？

**答案：** RTU 帧 = **从站地址（1 字节）+ 功能码（1 字节）+ 数据（N 字节）+ CRC16（2 字节，低字节在前）**，帧与帧之间至少 3.5 个字符时间的静默。没有报文头，所以接收方要靠功能码和字节数推算长度，靠静默时间判断帧边界。异常应答把功能码最高位置 1（`功能码 | 0x80`），后面跟一个异常码。RTU 帧最大 256 字节，PDU 最大 253 字节。

**背诵骨架：** 站号 + 功能码 + 数据 + CRC；低字节先发；3.5 字符分帧。

【项目】`ModbusRtuMaster.Transact` 先拼 PDU，再加站号和 CRC；`ReadResponse` 先读 3 字节头，判断是否异常应答，再按功能码算总长度。

### 67. Modbus TCP 的一帧长什么样？

**答案：** Modbus TCP = **MBAP 报文头（7 字节）+ PDU**。MBAP 包括：事务标识符（2 字节）、协议标识符（2 字节，Modbus 固定为 0）、长度（2 字节）、单元标识符（1 字节）。后面是功能码和数据。TCP 帧**没有 CRC**，靠 TCP 校验和与 MBAP 长度保证完整性；默认端口 502。一个 TCP 连接上可以连续发多帧，用**事务号**匹配请求和应答，避免应答串包。

**背诵骨架：** MBAP 7 字节 + PDU；事务号/协议号 0/长度/单元号；无 CRC；端口 502。

【项目】`ModbusTcpMaster` 每发一帧事务号加一，收到应答先比对事务号；`SemaphoreSlim` 保证同一连接上一问一答，不让多线程把应答搅乱。

---

### 68. MBAP 的长度字段表示什么？

**答案：** MBAP 的长度字段表示**它后面还有多少字节**，等于“单元标识符（1 字节）+ PDU 字节数”，**不包括** MBAP 前 6 字节，也不包括它自己。比如读 10 个寄存器的应答：单元号 1 + 功能码 1 + 字节数 1 + 数据 20 = 23，长度字段就是 23。接收方先读 7 字节 MBAP 头，再用长度字段算出后续要读多少字节，这是 TCP 拆包的关键。长度字段最大是 254（单元号 1 + PDU 253），实现里常按 260 字节的 ADU 上限做防御。

**背诵骨架：** 长度 = 单元号 + PDU；不含 MBAP 前 6 字节；用来拆包。

【项目】`ModbusTcpMaster.TransactAsync` 读到 `respLength` 后，再读 `respLength - 1` 字节（因为 7 字节头里已经包含了单元号），拼出完整 PDU。

### 69. 功能码 03 和 04 有什么区别？

**答案：** `03` 读**保持寄存器**（Holding Register），通常是可读可写的，地址习惯写成 4xxxx；`04` 读**输入寄存器**（Input Register），通常是只读的模拟量，地址习惯写成 3xxxx。两者返回的都是 16 位寄存器，报文结构一样，区别在**数据区和设备支持的功能**。写保持寄存器用 `06`（单个）或 `10`（多个）；输入寄存器一般不能写。到底用 03 还是 04，要看设备手册的点表，不能凭地址猜。

**背诵骨架：** 03 保持可写；04 输入只读；地址区不同；看手册。

【项目】`PollingService` 采集统一用 `ReadHoldingRegistersAsync`（03），因为配置里的点位按保持寄存器映射；如果设备把测量值放在输入寄存器，就要把读取方法改成 04，或把功能码做成配置项。

### 70. 40001 对应的 Modbus 地址是多少？★

**答案：** 传统 Modbus 的参考地址是**从 1 开始**的，而协议报文里的地址是**从 0 开始**的，所以 `40001` 通常对应协议地址 `0`。但现场并不统一：有的设备手册直接给 0 基地址，有的把 `40001` 映射成 `1`，还有的用 `400001` 这种六位写法。正确做法是看手册的“地址基数/偏移”说明，先用一个已知点位试读，确认后再批量配置。不要拿参考地址直接填进报文。

**背诵骨架：** 40001 → 0；设备可能不同基址；先看手册再试读。

【项目】`PointConfig.Address` 明确是 **0 基址**，直接用于报文；`PlcAddress` 只是给人看的显示字段（比如 `"40001"`），不参与通信。这样配置和协议地址不会混。

### 71. Modbus 异常码 02 是什么意思？

**答案：** 异常码 `02` 是 **Illegal Data Address（非法数据地址）**：请求的寄存器地址或数量超出了从站支持的范围，或者地址区选错了（比如把输入寄存器当保持寄存器读）。常见原因：地址基数搞错、点位表偏移、一次读的数量跨过了设备边界、设备根本不支持该地址。它不是接线问题，也不是 CRC 问题；先查手册地址范围，再用单点、小数量读取缩小范围。异常应答的功能码是原功能码最高位置 1，例如 `03` 变成 `83`。

**背诵骨架：** 非法地址；查基址/范围/数量；不是接线；异常功能码 `|0x80`。

【项目】`SelfCheck` 里专门构造了非法地址请求，模拟器返回异常码 `02`；`ModbusException` 会把功能码和异常码带出来，日志里能直接看到。

---

### 72. Modbus 异常码 0B 是什么意思？

**答案：** `0B` 是 **Gateway Target Device Failed to Respond（网关目标设备无响应）**：网关收到了请求，但下游的目标从站没有应答。常见原因：从站号配错、下游 485 线断/接反、从站没上电、网关的映射表没配、下游总线冲突。它和 `0A`（Gateway Path Unavailable，网关路径不可用）不同：`0A` 更像网关本身找不到路径，`0B` 是路径有了但目标设备不回。排查顺序是站号 → 网关映射 → 下游接线/电源 → 波特率。

**背诵骨架：** 网关找不到下游从站；查站号/映射/接线/电源；区别 0A。

---

### 73. 什么是字序 ABCD/CDAB？为什么容易出错？★

**答案：** Modbus 寄存器是 16 位的，32 位数据（`int32`、`float`）要拆成两个寄存器。**字序**决定哪个 16 位字在前：`ABCD` 是高字在前（标准大端），`CDAB` 是低字在前，`BADC` 是每个字内部字节交换，`DCBA` 是完全小端。以 `0x12345678` 为例：ABCD = `[0x1234][0x5678]`，CDAB = `[0x5678][0x1234]`，BADC = `[0x3412][0x7856]`，DCBA = `[0x7856][0x3412]`。字序错了，数值会“离谱但量级差不多”，很容易被误判成量程或传感器问题。32 位数据必须按点位配置字序，并用一个已知值验证。

**背诵骨架：** 高字在前/低字在前/字内交换/全小端；按点位配置；已知值验证。

【项目】`RegisterCodec` 支持 `Abcd/Badc/Cdab/Dcba` 四种字序，`PointConfig.Order` 每个点位单独配；`SelfCheck` 对四种字序做往返测试，确保编码解码一致。

### 74. 写线圈时 FF00 和 0000 分别代表什么？

**答案：** 功能码 `05` 写单个线圈时，数据区 `FF00` 表示 **ON**，`0000` 表示 **OFF**；其它值都是非法的。从站正常时会**原样回显**请求。写多个线圈用 `0F`，数据区按位打包，不是每个线圈两个字节。读线圈用 `01`，读离散输入用 `02`。不要把线圈和保持寄存器混用：线圈是位，寄存器是 16 位字。

**背诵骨架：** `FF00` 开、`0000` 关；05 单线圈、0F 多线圈；01 读。

【项目】`WriteSingleCoilAsync` 里就是 `value ? (ushort)0xFF00 : (ushort)0x0000`，发完检查应答功能码是否仍为 `05`。

---

### 75. 功能码 03 一次最多能读多少个寄存器？

**答案：** Modbus 规范规定 `03`/`04` 一次最多读 **125 个寄存器**（250 字节数据），因为 PDU 最大 253 字节。写多个寄存器 `10` 一次最多 **123 个**；读线圈 `01` 最多 **2000 个**；写多个线圈 `0F` 最多 **1968 个**。这些是协议上限，设备实际支持的数量可能更小，要以手册为准。超过上限要么拆成多次请求，要么减少点位。

**背诵骨架：** 读寄存器 125；写 123；读线圈 2000；写线圈 1968；设备可能更小。

【项目】`PollingService.MaxRegistersPerRead = 125`，`BuildGroups` 合并时保证每组的寄存器数量不超过 125；`ModbusRtuMaster`/`ModbusTcpMaster` 也会在入口校验 `1..125`。

### 76. 为什么要批量读寄存器？★

**答案：** RS485 是半双工总线，每一帧都有发送、等待应答、帧间隔的开销；如果 20 个点位每个都单独读，一个采集周期就要发 20 帧，总线负载和延迟都会上去，点位一多根本扛不住。把**地址相邻**的点位合并成一次 `03` 请求，可以显著减少帧数：中间有几个空地址，多读回来丢掉，通常也比多发一帧便宜。合并时要遵守单次 125 个寄存器的上限，并平衡“合并太多导致单帧变大、实时性变差”的问题。批量读是 485 采集最有效的优化之一。

**背诵骨架：** 少发帧；合并相邻地址；容忍小空档；上限 125。

【项目】`PollingService.BuildGroups` 把点位按地址排序，允许间隔不超过 2 个寄存器就合并；例如 100、101、102、105 会合成 `[100..105]` 一次读 6 个，中间 103/104 读回来丢弃。20 个点位通常能降到 2~4 帧。

### 77. 3.5 个字符时间是什么？

**答案：** Modbus RTU 没有帧头，靠**总线静默时间**判断一帧结束：帧与帧之间至少要有 **3.5 个字符时间**的静默。一个字符时间取决于波特率和帧格式，比如 9600-8-N-1 下每字符 10 位，约 1.04ms，3.5 字符约 3.65ms。波特率高于 19200 时，规范建议固定用 1.75ms。发送方在两次请求之间要留够这个间隔，否则从站可能把两帧粘成一帧；接收方也靠它判断帧边界。

**背诵骨架：** 3.5 字符静默；9600 约 3.65ms；高波特率固定 1.75ms；帧边界。

【项目】`ModbusRtuMaster.WaitInterFrameDelay` 按数据位、校验位、停止位算出每字符位数，再算 3.5 字符时间，并设了 2ms 下限；每次发送前根据上一帧的时间戳等待足够间隔。

### 78. TCP 心跳有什么用？

**答案：** TCP 连接可能变成**半开**：网线拔了、设备断电、NAT/防火墙超时，双方都不一定能立刻收到 FIN/RST，程序以为还连着，实际发出去的数据没人收。心跳就是定期发一个轻量请求（或利用 TCP KeepAlive），确认链路还活着；连续失败就判定断线，关闭连接并重连。心跳间隔要结合实时性要求，太频繁增加负担，太稀疏发现慢。应用层心跳比 TCP KeepAlive 更可控，因为可以带业务语义。对 Modbus 来说，周期采集本身就可以充当心跳。

**背诵骨架：** 检测半开连接；保活/应用层心跳；失败重连；采集本身可当心跳。

【项目】采集循环每 500ms 读一次寄存器，读成功就说明链路正常；连续失败会记录日志、把设备标记为离线、上报 `Bad` 质量，然后断开重连，不需要额外的心跳线程。

### 79. 西门子 S7 通信有什么特点？

**答案：** S7 通信通常走 **TCP 102 端口**，基于 ISO-on-TCP（RFC1006），上层是 S7comm 协议；数据按 **DB/I/Q/M** 等区域组织，读 DB 块要指定 DB 号、起始字节和长度，还要注意机架号/槽号。S7 数据是**大端**，和多寄存器字序问题类似。不同 PLC 型号（S7-1200/1500、S7-300/400、S7-200 SMART）细节有差异，有的要开启 PUT/GET、有的要配优化块访问。实际项目常用 S7.Net、Sharp7 这类库，不必从零手写协议。

**背诵骨架：** 102 端口；ISO-on-TCP；DB 偏移；大端；型号差异。

【实验】我按课程文档做过 S7 连接和读 DB 块的实验，理解了 DB 号/偏移和字节序；但还没有在生产设备上长期跑过，面试时我会明确说是实验环境。

### 80. OPC UA 有什么优势？

**答案：** OPC UA 是跨平台、面向服务的工业通信标准，核心优势是**信息模型自描述**：服务器不仅给数据，还给类型、单位、语义，客户端可以浏览地址空间；支持**订阅**（数据变化才推送，不用轮询）、**安全**（证书、签名、加密）、会话和用户认证；还支持历史数据、报警、方法调用，适合 SCADA/MES 集成。默认端口 4840。代价是协议重、实现复杂、资源占用比 Modbus 高；简单设备采集用 Modbus 更轻，系统集成和跨厂商互通用 OPC UA 更合适。

**背诵骨架：** 自描述、订阅、安全、跨平台；4840；重但适合集成。

【实验】课程里做过 OPC UA 的连接/浏览实验，知道节点、订阅和安全策略的概念；生产项目选型时我会根据对端设备和系统集成需求决定用 Modbus 还是 OPC UA。

## 六、数据库与数据存储（81~90）

### 81. 历史数据表应该怎么设计？★

**答案：** 核心是**窄表**：一张历史表存 `TagId`、`Timestamp`、`Value`、`Quality`，需要时再加 `DeviceId`、`Alarm` 等字段，而不是每个点位建一张表或每天建一张表。索引一般建在 `(TagId, Timestamp)` 上，因为查询通常是“某个点位在某段时间的数据”；如果经常按设备/时间查，再加对应联合索引。数据量大时按时间**分区**或按月分表，原始数据短期保留、长期数据降采样或归档。值用 `double` 存工程值，同时保留质量码，避免“0”和“没采到”混淆。

**背诵骨架：** 窄表；位号+时间+值+质量；联合索引 `(TagId, Ts)`；按时间分区。

【项目】现在 CSV 的列就是 `时间,设备,位号,数值,单位,质量,报警`，本质是窄表；数据量上来后换成 SQLite/SQL Server，表结构可以按这个思路建，查询接口不用大改。

### 82. 索引有什么用？为什么不能乱建？

**答案：** 索引（常见是 B-tree）能加速 `WHERE`、`JOIN`、`ORDER BY` 的查找，减少全表扫描；唯一索引还能保证约束。代价是**写入变慢**：每次插入/更新/删除都要维护索引，而且占磁盘。联合索引要注意**列顺序**，通常把等值条件、选择性高的列放前面，范围查询列放后面；能覆盖查询的索引更好。索引不是越多越好，低选择性的列单独建索引收益很小。上线前看执行计划，别凭感觉建。

**背诵骨架：** 加速读、拖慢写、占空间；联合索引看顺序；看执行计划。

【项目】CSV 没有索引，查一天数据只能顺序扫；换成 SQLite 后会在 `(TagId, Timestamp)` 上建索引，按点位+时间查历史就会走索引。

### 83. 事务的 ACID 是什么？

**答案：** **原子性（Atomicity）**：事务里的操作要么全成功，要么全回滚；**一致性（Consistency）**：事务前后数据满足约束；**隔离性（Isolation）**：并发事务之间互不干扰，隔离级别越高并发越低；**持久性（Durability）**：提交后的数据即使断电也不丢。典型例子是批量插入历史数据：要么整批写成功，要么一条都不写。实现上依赖日志、锁/MVCC 和刷盘。事务要尽量短，不要在事务里做网络请求或等用户输入。

**背诵骨架：** 原子/一致/隔离/持久；批量插入一个事务；事务要短。

【项目】CSV 写入没有事务语义，只能保证“一批一次写、尽量 flush”；如果换成 SQLite，一批历史数据放在一个事务里提交，掉电时要么全有要么全无。

---

### 84. 批量插入怎么优化？★

**答案：** 核心是**减少提交次数和往返**：把一批数据放在**一个事务**里，用**参数化命令**或预编译语句，多条 `INSERT` 合并成多值插入，按几百到几千条一批提交；导入历史数据时可以临时关闭索引/触发器、调整 `PRAGMA synchronous`（SQLite）或使用 `SqlBulkCopy`（SQL Server）。不要一行一个事务、不要拼 SQL 字符串（注入风险、执行计划难复用）。批量大小要测，太大可能锁表、日志暴涨、内存占用高。

**背诵骨架：** 一个事务 + 参数化 + 多行插入 + 批量提交；别一行一提交。

【项目】`MainForm` 的定时器每次最多从 `ConcurrentQueue` 取 5000 条，交给 `CsvHistoryStore.Append` 一次写入并 `Flush`；换数据库后对应做法就是“一个事务 + 预编译 + 批量提交”。

---

### 85. SQLite 适合什么场景？

**答案：** SQLite 是**嵌入式**数据库：一个文件、零安装、跨平台、支持事务和 SQL，适合单机上位机的本地历史库、配置库、报警记录。缺点是**写并发弱**：同一时刻通常只有一个写者，多个客户端同时写会锁等待；它没有网络服务端，不适合多台电脑共享。可以用 WAL 模式提升读写并发，但不要把 SQLite 当 MySQL/SQL Server 用。数据量到百万行以上、需要复杂查询或多客户端时，应该换客户端/服务器数据库。

**背诵骨架：** 嵌入式、单文件、零部署；单机；写并发弱；WAL；不适合多客户端。

【项目】现在用 CSV 是为了零依赖、Excel 可直接打开、现场排障方便；单机历史查询量再大一点，SQLite 是自然的下一步，接口层可以替换。

---

### 86. SQL Server 适合什么场景？

**答案：** SQL Server 是**客户端/服务器**数据库，适合多客户端并发、局域网集中部署、需要权限、备份、作业、报表和运维体系的场景。它提供高并发、事务、存储过程、复制、AlwaysOn 等能力，但需要安装、授权和运维，成本比 SQLite 高；Express 版有容量和资源限制。选型要看客户端数量、数据量、网络环境、客户 IT 规范和预算，不是“功能多就选它”。

**背诵骨架：** 客户端/服务器；多用户并发；权限/备份/运维；成本高。

【项目】如果一套上位机要给多台操作站同时查历史、还要对接 MES，我会选 SQL Server；单机设备本地存历史，SQLite 就够了。

### 87. 什么是死区（Deadband）？

**答案：** 死区是“变化小于阈值就不存”的压缩策略：只有工程值相对上次存储值的变化超过死区，或者超过最大存储间隔，才写一条历史。它能大幅减少无效数据（比如温度长期稳定在 25.0℃），降低存储和查询压力。死区要按点位配置，不能太大，否则会掩盖缓慢漂移；**质量变化、报警状态变化必须无条件存储**，否则回放历史时会漏掉故障。死区通常按工程值算，不是按原始寄存器值算。

**背诵骨架：** 变化超阈值才存；加最大间隔；状态变化必须存；按点位配。

【项目】当前 `MainForm` 对 Good 质量的每个快照都入队落盘，数据量随时间线性增长；如果长期运行，我会加死区 + 最大间隔，并在报警/质量变化时强制落盘。

---

### 88. 什么是降采样？

**答案：** 降采样是把高频原始数据聚合成更低频的摘要，比如把秒级数据按分钟算平均/最大/最小/最后值，或按小时聚合。目的不是“丢数据”，而是让长时间范围的查询和图表更快：查一年趋势不需要返回几千万个点，返回每小时一个聚合值就够了。常见做法是原始数据短期保留，聚合表长期保留；查询时按时间范围自动选择粒度；图表也可以用分桶或 LTTB 之类的算法减少点数。

**背诵骨架：** 按分钟/小时聚合；平均/最大/最小/最后；原始短期、聚合长期；图表降采样。

【项目】趋势图最多保留 1500 个点，超出丢最旧的；如果要做“查一个月趋势”，不能把原始点全塞进图里，而应该先按时间桶聚合再画。

---

### 89. 历史数据怎么清理？

**答案：** 先定**保留策略**：原始数据保留多少天、聚合数据保留多久、报警保留多久。清理优先按**时间分区/按天文件**删除，避免一条大 DELETE 长时间锁表；删除后 SQLite 需要 `VACUUM` 回收空间（或合理配置 auto_vacuum），SQL Server 可以分区切换/重建索引。清理任务放在低峰期，先归档再删除，失败要能重试。不要用 `DROP` 整表代替正常清理，除非确认数据不再需要。

**背诵骨架：** 保留策略；按天/分区删；归档；VACUUM；低峰执行。

【项目】`CsvHistoryStore.Cleanup` 按文件名里的日期删除超过保留天数的 CSV；文件被 Excel 占用时删除会失败，代码里捕获并跳过，下次再清。

### 90. 密码应该怎么存？

**答案：** 绝不能明文存，也不要用 MD5/SHA1 这类快速哈希单独存。正确做法是**每个用户一个随机盐**，用**慢哈希**算法（PBKDF2、bcrypt、Argon2）计算哈希，存“算法 + 参数 + 盐 + 哈希”，验证时用同样参数计算并做**恒定时间比较**。迭代次数/内存成本要按当前推荐配置，太低容易被暴力破解，太高会影响登录性能。密码不能写日志、不能出现在异常信息里；数据库权限最小化，传输层用 TLS。

**背诵骨架：** 随机盐 + 慢哈希（PBKDF2/bcrypt/Argon2）；存参数；恒定时间比较；绝不明文/MD5。

【项目】当前项目没有用户体系；如果加操作员登录和权限，我会用 PBKDF2/bcrypt 存哈希，而不是在 JSON 配置里放明文密码。

## 七、工程化、现场与求职（91~100）

### 91. 现场设备连不上，你怎么排查？★

**答案：** 按**从物理到软件**的顺序查，一次只改一个变量：① 物理层——设备供电、A/B 线是否接反/松动、转换器是否正常、终端电阻、接地；② 串口参数——COM 口、波特率、数据位、校验、停止位是否和手册一致；③ 站号/地址——从站号、地址基数、点位表是否对应；④ 协议层——功能码、寄存器类型、字节/字序、数量是否越界；⑤ 程序层——端口被占用、防火墙、超时、权限、代码是否连错 IP/站号。工具上用模拟器、Modbus Poll、串口回环、抓包/示波器逐层验证；同时看日志里的超时、CRC、异常码，先问客户“之前通过吗、最近改了什么、是单台还是全部”。

**背诵骨架：** 物理 → 参数 → 地址 → 协议 → 程序；一次只改一个变量；日志+工具。

【项目】我有 Python 从站模拟器和 `SelfCheck`，可以先排除上位机代码问题；现场则按“电源/接线 → 串口参数 → 站号/地址 → 功能码/字序 → 程序”的顺序查，日志里能看到具体是超时、CRC 错还是异常码。

---

### 92. 偶发 CRC 错误一般是什么原因？★

**答案：** 偶发 CRC 错通常不是协议代码本身，而是**信号质量**问题：变频器/电机干扰、屏蔽层接地不当、终端电阻缺失、A/B 线松动或接反、线太长/波特率太高、总线星形分支、设备之间地电位差。先统计错误率（偶发一次还是每分钟多次），再检查布线是否远离动力线、是否用双绞屏蔽线、终端电阻是否只在两端、屏蔽层是否单端接地、是否需要隔离器。重试只能掩盖问题，不能根治；如果重试后仍频繁出错，必须查物理层。

**背诵骨架：** 干扰/终端/接地/线序/波特率；先统计错误率；重试不治本。

【项目】`ModbusRtuMaster` 校验失败会抛带帧十六进制的异常，日志能看出是 CRC 错还是超时；现场偶发 CRC 错时，我会先看错误频率和发生时段，再查变频器启停、接地和终端电阻。

---

### 93. 读上来的数据跳变/明显不对，怎么查？★

**答案：** 先看**原始寄存器值**，不要只看换算后的工程值。常见原因：字序/字节序配错（32 位数据最常见）、数据类型不对（有符号/无符号、int/float）、量程 `scale/offset` 错、寄存器地址映射错、把两个不同点位拼在一起、设备内部单位不同、干扰导致偶发坏值。用一个**已知值**（比如设定 25.0℃）对照手册和原始报文，逐项排除；改一个参数看结果，不要同时改字序和量程。若只是偶发跳变，还要查接线、接地和采样滤波。

**背诵骨架：** 先看原始寄存器；字序/类型/量程/映射；已知值验证；一次改一个。

【项目】`RegisterCodec` 把字序、数据类型、`scale/offset` 分开配置；`SelfCheck` 对四种字序做往返测试。现场遇到数值离谱，我会先把原始寄存器打印出来，对照手册算一遍，再决定改哪一项。

---

### 94. 程序运行久了内存一直涨，怎么查？★

**答案：** 常见原因：**事件订阅没退订**（采集服务持有窗体/ViewModel，窗体关了也回收不了）、**集合无限增长**（报警列表、日志、趋势点）、**句柄/连接没释放**（串口、Socket、GDI 对象）、**静态缓存只增不减**、大对象堆碎片。排查用内存 profiler（dotnet-counters、dotnet-dump、PerfView、ANTS/dotMemory）看对象数量和根引用，抓两次 dump 对比；不要只看任务管理器的“内存”数字。修复包括：关闭时退订事件、给集合设上限/滚动删除、`using`/`Dispose`、缓存加过期策略。

**背诵骨架：** 事件未退订/集合无限长/句柄未释放/静态缓存；profiler 对比 dump；退订+上限+Dispose。

【项目】`MainForm` 关闭时会 `SnapshotReady -= OnSnapshotReady`，避免服务持有窗体；趋势图最多 1500 个点，超出删最旧的；报警列表最多 500 条；串口/Socket 都通过 `Dispose` 释放。这些就是针对内存和资源泄漏做的。

### 95. 断电会丢数据吗？怎么保证？

**答案：** 会。数据可能还在**操作系统缓存**里，没真正落盘；程序被强杀、机器断电、磁盘故障都会丢。保证手段：数据库用**事务 + WAL/日志 + 合适的 fsync 策略**，文件写入后调用 `Flush(true)` 强制刷盘；关键数据用 UPS；定期备份并验证可恢复；明确业务能接受丢多少（RPO）。不要依赖“关窗时再保存”，因为断电不会给你关窗的机会。性能和数据安全要权衡，`synchronous=FULL` 更安全但更慢。

**背诵骨架：** OS 缓存/未刷盘；事务/WAL/fsync；UPS；备份；明确 RPO。

【项目】CSV 每批写完调用 `Flush`，但它主要刷到操作系统缓存；要抗突然断电，应该用 `FileStream.Flush(true)` 或换 SQLite 事务。这是我目前项目的一个边界，面试时可以主动说明。

### 96. 日志应该怎么设计？

**答案：** 至少要有**级别**（Debug/Info/Warn/Error/Fatal）、**时间**、**来源/线程**、**上下文**（设备、站号、点位、报文）、**异常堆栈**；按天或按大小**滚动**，设置**保留期**，避免磁盘被写满；高频日志要异步/缓冲写，UI 日志窗口要有上限，不能无限追加。敏感信息（密码、密钥）不能打日志。生产环境用 Serilog/NLog 这类成熟库，支持结构化日志和多种输出；排查时用同一个请求/设备 ID 串起来。日志失败不能把主流程带崩。

**背诵骨架：** 分级/滚动/保留期/上下文/异常堆栈；异步写；UI 有上限；别打敏感信息。

【项目】`Log` 按天写 `logs/yyyyMMdd.log`，启动时清理 30 天前的文件，写入用 `lock` 串行化，日志失败被吞掉不影响采集；UI 可以订阅 `MessageWritten`，但回调在后台线程，更新界面要 `Invoke`。

### 97. 上位机怎么打包部署？★

**背诵骨架：** 框架依赖/自包含/单文件；`dotnet publish`；配置和数据目录；安装包；干净机验证。

### 98. 软件升级怎么保证兼容？★

**背诵骨架：** 配置版本+默认值；数据库迁移；备份+回滚；小范围试点。

### 加练 1：生产者-消费者

```csharp
using System.Collections.Concurrent;

var queue = new BlockingCollection<int>(boundedCapacity: 100);

var producer = Task.Run(() =>
{
    for (var i = 0; i < 100; i++)
        queue.Add(i);
    queue.CompleteAdding();
});

var consumer = Task.Run(() =>
{
    foreach (var item in queue.GetConsumingEnumerable())
        Console.WriteLine(item);
});

await Task.WhenAll(producer, consumer);
```

**要点：** `BlockingCollection` 自带阻塞和线程安全；`CompleteAdding` 通知消费者结束；有界容量可以形成背压。

### 加练 2：HEX 字符串转字节数组

```csharp
public static byte[] ParseHex(string text)
{
    var clean = text.Replace(" ", "")
                    .Replace("-", "")
                    .Replace("\r", "")
                    .Replace("\n", "");
    if (clean.Length % 2 != 0)
        throw new FormatException("HEX 长度必须是偶数");

    var result = new byte[clean.Length / 2];
    for (var i = 0; i < result.Length; i++)
        result[i] = Convert.ToByte(clean.Substring(i * 2, 2), 16);
    return result;
}
```

**要点：** 先去掉空格/分隔符；长度为奇数要报错；`Convert.ToByte(..., 16)` 遇到非法字符会抛异常，调用方要处理。

### 加练 4：冒泡排序（带提前退出）

```csharp
public static void BubbleSort(int[] a)
{
    for (var i = 0; i < a.Length - 1; i++)
    {
        var swapped = false;
        for (var j = 0; j < a.Length - 1 - i; j++)
        {
            if (a[j] <= a[j + 1]) continue;
            (a[j], a[j + 1]) = (a[j + 1], a[j]);
            swapped = true;
        }
        if (!swapped) break;
    }
}
```

**要点：** 平均/最坏 O(n²)，最好 O(n)（已经有序）；加 `swapped` 提前退出；面试一般还会问快排的分区和复杂度。

### 加练 5：单例（`Lazy<T>` 版）

```csharp
public sealed class Singleton
{
    private static readonly Lazy<Singleton> _instance =
        new(() => new Singleton(), LazyThreadSafetyMode.ExecutionAndPublication);

    public static Singleton Instance => _instance.Value;

    private Singleton() { }
}
```

**要点：** 私有构造防止外部 `new`；`Lazy<T>` 默认线程安全；`sealed` 防止继承破坏单例；更推荐用 DI 容器的 Singleton 生命周期。

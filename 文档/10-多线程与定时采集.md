# 10 多线程、定时采集与线程安全

> 本章目标：写出“连续跑 8 小时不卡、不崩、能优雅退出”的采集程序。
> 这是上位机从“能演示”到“能交付”的分水岭。

---

## 1. 为什么上位机必须多线程

- 串口读、网络读都是**阻塞**的：同步等 1 秒，界面就冻结 1 秒。
- 采集要按周期一直跑：不能占着 UI 线程。
- 存盘、报表、导出可能很慢：不能拖累采集。

基本模型：

```
UI 线程：只负责画界面、响应点击
采集线程：按周期读设备 → 解析 → 抛事件
存盘线程：批量写数据库
```

---

## 2. Thread / Task / Timer 怎么选

| 方式 | 适用 | 注意 |
|---|---|---|
| `Thread` | 长期独占线程（少见） | 手动管理，不推荐 |
| `Task.Run` | 后台一次性工作 | 别在里更新 UI |
| `Task` + `async/await` | I/O 密集（网络） | 首选 |
| `System.Windows.Forms.Timer` | UI 定时刷新 | 在 UI 线程触发，别做耗时操作 |
| `System.Timers.Timer` | 后台定时 | 回调在线程池，注意重入 |
| `PeriodicTimer` | 现代周期任务 | `await timer.WaitForNextTickAsync(ct)` |

本仓库采集用 `Task.Run` + 循环 + `Task.Delay`，好处是：**能取消、能等待、能统一异常处理**。

```csharp
while (!ct.IsCancellationRequested)
{
    var clock = Stopwatch.StartNew();
    try
    {
        var values = await ReadAllAsync(ct);
        RaiseSnapshot(values);
    }
    catch (OperationCanceledException) { break; }
    catch (Exception ex) { Log.Error("采集失败", ex); }

    var wait = Math.Max(50, device.PollIntervalMs - (int)clock.ElapsedMilliseconds);
    await Task.Delay(wait, ct);
}
```

关键细节：**用 Stopwatch 扣掉本次采集耗时**，否则实际周期 = 采集耗时 + 间隔，越跑越慢。

## 3. 定时器的重入陷阱

```csharp
// 危险：上一次没跑完，下一次又进来了
timer.Elapsed += async (s, e) => await ReadDeviceAsync();
```

如果 `ReadDeviceAsync` 要 3 秒，而定时器 1 秒触发一次，就会并发读同一个串口 → 数据错乱。

三种修法：

```csharp
// 1. 加锁（简单粗暴，会堆积）
lock (_gate) { /* 读 */ }

// 2. 用标志位跳过本次
private int _busy;
if (Interlocked.Exchange(ref _busy, 1) == 1) return;
try { await ReadAsync(); } finally { Interlocked.Exchange(ref _busy, 0); }

// 3. 改成 while 循环（推荐）
while (!ct.IsCancellationRequested) { await ReadAsync(); await Task.Delay(500, ct); }
```

## 4. 线程安全

### 4.1 共享数据的四种保护

```csharp
// lock：最简单，别锁 this、别锁字符串
private readonly object _sync = new();
lock (_sync) { _list.Add(item); }

// Interlocked：计数器
Interlocked.Increment(ref _rxBytes);

// 并发集合：多线程读写
var queue = new ConcurrentQueue<HistoryRecord>();
queue.Enqueue(record);
if (queue.TryDequeue(out var r)) { }

// 不可变：最安全
var snapshot = _points.ToArray();   // 对外只给副本
```

### 4.2 一个经典竞态

```csharp
// 错误：count++ 不是原子操作
if (count < 10) count++;

// 正确
if (Interlocked.Increment(ref count) <= 10) { }
```

### 4.3 UI 线程

```csharp
// WinForms
if (InvokeRequired) BeginInvoke(new Action(UpdateUi));
else UpdateUi();

// WPF
Dispatcher.BeginInvoke(new Action(UpdateUi));
// 或 ViewModel 里捕获 SynchronizationContext
_uiContext.Post(_ => UpdateUi(), null);
```

**采集线程里绝对不要直接 `label.Text = ...`。**

## 5. 生产者-消费者：采集与存盘解耦

采集快、存盘慢时，用队列缓冲：

```csharp
private readonly Channel<HistoryRecord> _channel =
    Channel.CreateBounded<HistoryRecord>(new BoundedChannelOptions(100_000)
    {
        FullMode = BoundedChannelFullMode.DropOldest
    });

// 生产者（采集）
await _channel.Writer.WriteAsync(record, ct);

// 消费者（存盘）
await foreach (var record in _channel.Reader.ReadAllAsync(ct))
{
    buffer.Add(record);
    if (buffer.Count >= 1000) { store.Append(buffer); buffer.Clear(); }
}
```

要点：

- **有界队列**，防止内存无限增长；
- 满了的策略要明确（丢最旧 / 阻塞 / 报警）；
- 退出时把剩余数据刷完。

## 6. 取消与优雅退出

```csharp
private CancellationTokenSource? _cts;

public void Start()
{
    _cts = new CancellationTokenSource();
    _worker = Task.Run(() => LoopAsync(_cts.Token));
}

public async Task StopAsync()
{
    _cts?.Cancel();
    try { await _worker!; } catch (OperationCanceledException) { }
    _cts?.Dispose();
    _cts = null;
}
```

窗体关闭：

```csharp
private void MainForm_FormClosing(object? sender, FormClosingEventArgs e)
{
    _closing = true;
    _service?.StopAsync().Wait(1500);   // 给采集线程 1.5 秒收尾
    FlushHistory();                      // 把队列里的数据写完
}
```

**不优雅退出的后果**：程序关了但进程还在、串口被占用、"端口被占用"报错、最后一批数据丢失。

## 7. async/await 五个死坑

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `.Result` / `.Wait()` | UI 死锁 | 用 `await` |
| `async void` | 异常直接崩进程 | 除事件处理器外用 `async Task` |
| 忘记 `ConfigureAwait(false)` | 库代码回 UI 线程，性能差 | 类库加，UI 不加 |
| 不传 `CancellationToken` | 关不掉 | 每个长任务都传 |
| `Task.Run` 里更新 UI | 跨线程异常 | 回到 UI 线程再更新 |

死锁原理（面试必问）：

```
UI 线程调用 .Result → 阻塞等待任务完成
任务内部 await 需要回到 UI 线程 → 但 UI 线程被阻塞 → 互相等待 → 死锁
```

## 8. 采集性能预算

假设：20 个点位、500ms 周期、Modbus RTU 9600。

```
每帧：请求 8 字节(约 8.3ms) + 应答 45 字节(约 47ms) + 静默 4ms ≈ 60ms
20 个点若单点读：20 × 60ms = 1.2s > 500ms   ← 根本跑不过来
合并成 2 帧：2 × 60ms = 120ms                ← 轻松
```

所以：

1. **批量读**是第一优化手段；
2. 周期不要小于“一帧耗时 × 帧数”；
3. 点位特别多时，分设备并行（不同串口/不同网口）；
4. 界面刷新频率可以低于采集频率（采 500ms，界面 1s 刷一次）。

## 9. 本仓库采集引擎讲解

`Industrial.Core/Services/PollingService.cs`：

```csharp
public sealed class PollingService : IAsyncDisposable
{
    public event Action<IReadOnlyList<TagValue>>? SnapshotReady;
    public event Action<string, bool>? DeviceStateChanged;

    public void Start() { /* 每台设备一个 Task */ }
    public async Task StopAsync() { /* Cancel + WhenAll */ }
}
```

设计要点：

| 设计 | 解决的问题 |
|---|---|
| 每设备独立循环 | 一台设备掉线不影响其他设备 |
| 批量分组读取 | 485 总线性能 |
| 失败上报 Bad | 界面能显示故障，不显示过期值 |
| 事件抛出快照 | UI 与采集解耦 |
| StopAsync 等待 | 优雅退出 |
| 2000ms 重连间隔 | 避免狂连拖垮网络 |

## 10. 排查多线程问题

| 现象 | 工具/方法 |
|---|---|
| 界面卡顿 | 调试暂停看 UI 线程堆栈 |
| 数据错乱 | 检查是否有共享可变状态没加锁 |
| 偶发崩溃 | 全局异常 + 日志堆栈 |
| 退出后进程残留 | 检查是否有前台线程/未取消的 Task |
| CPU 高 | 性能监视器 + 看是否空转 |
| 死锁 | 抓 dump（任务管理器 → 创建转储）分析 |
